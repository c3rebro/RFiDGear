# Developer Notes

## One-attempt rule
Operations that change card state (authentication, file creation, key rotation, etc.) must only be attempted once per request. The provider layer should rely on the caller to orchestrate retries rather than automatically repeating failed calls. Automatic retries can leave a reader or card in an undefined state and mask the original failure reason. When a command fails, return the appropriate error code and let the orchestrator decide whether to re-run the task.

## Normalized provider error codes
The provider layer now returns a small, normalized set of error codes to make downstream handling consistent. These codes are surfaced by `ReaderDevice` and its implementations and should be propagated without collapsing distinct conditions into a generic catch-all:

- `AuthFailure`: authentication or key negotiation failed.
- `PermissionDenied`: access was explicitly refused by policy or configuration.
- `ProtocolConstraint`: the requested operation violated protocol constraints (e.g., resource already exists, limits exceeded).
- `TransportError`: communication problems such as unavailable readers or timeouts.
- `Unknown`: unexpected state or unclassified errors that do not map to the categories above.
- `KeyUnavailable` (set by a task command, not by a reader): a key slot is bound to a secure key provider and the key could not be obtained. The command made no card call and used no other key.

When you add or update provider logic, choose the most specific code that matches the condition so that calling layers can react accurately (e.g., prompting for different credentials versus retrying the connection).

## The Windows Credential Manager as a secure key provider
RFiDGear brings one secure key provider of its own, `windows-credential-manager` (`WindowsCredentialKeyProvider`). A task slot that is bound to it holds a reference instead of a key, and the key is read from the Credential Manager when the task runs.

- The id is stored in project files and never changes. Extensions cannot take it over.
- A reference is the name of a generic credential below the fixed prefix `RFiDGear/key/`. Whatever a project says, the name that reaches the vault starts with that prefix, so a project cannot read the credential of another application.
- The credential holds the hexadecimal digits of the key as UTF-16 text, which is how `cmdkey` stores a password: 12 digits for a MIFARE Classic key, 32 for a DES or AES key, 48 for a 3K3DES key. Without a tool of ours, a key is stored with `cmdkey /generic:RFiDGear/key/<reference> /user:RFiDGear /pass`, which asks for the digits at a prompt. Do not write them on the command line (`/pass:<digits>`): other programs can read a command line, and shell histories and process logs keep it. The prompt reads from the console, so a test cannot drive it; a test stores a dummy value with `/pass:<digits>` to pin the format that the tool writes, and reads it back.
- What it protects against is a key that ends up in a project file, a backup or an e-mail. It does not protect against a program that runs as the same user: the Credential Manager gives the secret to every process of that user.
- The conversion from the stored text to the key works on the bytes and never makes a string, because a string cannot be erased. The copies of the secret that the vault hands out are erased, and the arrays that hold one are on the pinned object heap, so the garbage collector never leaves an old copy behind.
- `ICredentialStore` is the seam in front of the vault. The tests use a dictionary; one test uses the real vault with a name of its own and removes it.

## Key slot editors and the key manager in the task dialogs
Every box in which a card key is typed is wrapped by `KeySlotEditor` (`Views/KeySlotEditor.xaml`): the sixteen key boxes of the DESFire card mastering, application mastering and data explorer tabs and of the MIFARE Classic key tab. The wrapper shows that a slot names its key by a reference to a secure key provider instead of holding it typed. The choice itself is made in the key manager (next section), which a button at the bottom of each section of keys opens.

```xml
<ctl:KeySlotEditor Grid.Row="0" Grid.Column="1" Host="{Binding}" SlotId="desfire.read">
    <TextBox Text="{Binding DesfireReadKeyCurrent, UpdateSourceTrigger=PropertyChanged, Mode=TwoWay}" ... />
</ctl:KeySlotEditor>
```

- The wrapped box keeps everything it had: its style, its tool tip, its validity colours, its `MaxLength`. Only the grid placement and the `Visibility` move to the wrapper. `SlotId` is an id of `SecureKeySlots`; `Host` is the task and has to implement `IKeySlotHost`, which both setup view models do.
- What a slot decides is in `KeySlotEditorState`, with the question to the person behind `IKeySlotEditorDialogs` (only `ConfirmReplaceKey`), so that it is tested without a window. Switching a slot that holds a key to a reference asks first (a slot without a key is switched without a question). The binding is written first and the key is cleared second, so the slot is never left with neither. The state has no window of its own any more; the editor and the key manager both show it.
- While a slot is bound, the wrapped box is disabled and shows `State.ReferenceCaption` (`Reference: <name>`) in the place of the key, and its tooltip is the key store and the name (`State.ReferenceDetail`). Nothing lies over the box and nothing is added below it, so the layout does not change and a long name cannot widen a column (the text is cut at the box). The editor does this to the box the view brought: it replaces the binding of its `Text` to the key of the task with a one-way binding to the caption, sets a neutral background (an empty key is invalid, and the view's own style would paint it red), and sets the tooltip; `SavedValue` keeps the binding, the background and the tooltip the box had, and puts them back when the slot is typed again. Nothing typed or shown there can reach the key of the task while it is gone. In the Classic tab the boxes are about 64 px wide, so only the start of the caption shows there; the tooltip has all of it.
- The editor is one cell that the box fills. The key boxes have no height of their own: they stretch to their row, which the label beside them sets (26 px in the card mastering tab). An editor that is two rows high (a box and a caption) stops that stretch, and the box shrinks to the height of its text (18 px); a test asks for 26, and for every stretching box to fill its cell, typed and bound.
- A section of keys has a `KeyManagerButton` at the bottom of its group box, with the height, the padding and the margins of the buttons around it. It is not bound to a list of slots: it looks for the visible `KeySlotEditor`s in its nearest `GroupBox`, in screen order, so `desfire.app.old` is in the manager only while its box is shown. Without the button a visible, bound key would have no way to be changed back, which is why the editor has no button of its own.
- While the keys of a command are obtained from their providers (`IsFetchingKeys`), the tabs of the dialog take no input (`AreInputsEnabled`): what a person changes meanwhile would no longer be what the keys were asked for.
- A new key box needs the wrapper, a slot id, a name for the slot (`keySlotName...` in both resource files, mapped in `KeySlotNames`; a test fails for a slot without one), and a `KeyManagerButton` in its section. `KeySlotEditorViewTests` lists the slots of every tab and fails when a key has no editor, and sweeps every task type of the DESFire and Classic tabs: every visible editor has a visible, enabled button in its own group box.
- A tab has less room in its dialog than alone in a window: the task above it and the status below it take their part, and the tab gets about three quarters of what the window gains in height. The tests therefore also show the real dialogs, at the smallest size each declares (`MinWidth`, `MinHeight`) and at the default, for every task type, typed and bound, and fail when a manager button ends below the group box of its section (the space it keeps below it counts) or the group box below the area of the tab. The button of the right-hand group of the DESFire application mastering tab needed the minimum and the default height of the DESFire dialog to go from 700 and 750 to 760, and the data explorer (whose right-hand group was already wider than the dialog at 900) the minimum width to go from 900 to 990. If a section grows again, raise the size rather than let the button, the only way back from a reference, be cut off.
- In the Classic key tab, WPF clamps an out-of-range `Grid.Row` to the last row. The sub-boxes of the MAD sections have to name their row (`Grid.Row="2"`) before a row is appended to their grid, or they move down with it.
- `x:Static` cannot reach a constant of an internal class: such a value is set in the code-behind.

## The key manager
`KeyManagerView` (`Views/KeyManagerView.xaml`) is a modal window that the button opens with the task dialog as its owner; `KeyManagerViewModel` has one `KeyManagerSlotRow` for each slot, and each row is a thin face on a `KeySlotEditorState`. Nothing is staged: a choice is written to the task at once, and the task dialog drops its copy when it is cancelled, so the window has a Close button and no OK and Cancel. `IKeyManagerLauncher` (`WpfKeyManagerLauncher`) shows it, so the view models do not know a window.

- A row says "Use reference" or "Use typed key". With a reference it has the key store and then, for the Credential Manager, two separate things: the **stored key**, a list of the names that exist (`KeyManagerSlotRow.StoredKeys`, from `ICredentialStore.Enumerate`; no key is read), and a group **Create a new key** with a name, the entry for the key, and "Store key". Choosing a name binds the slot to it. A key store that is not the Credential Manager (the connected application) takes a typed name and has neither the list nor the group. The slot's own name stays in the list even when no such key is stored, marked "(not stored)", so the list shows what the slot does and a missing key is seen as missing; a list that is emptied while its items are replaced reports no choice, which the row ignores (`Reference` takes no `null`), or it would unbind the slot.
- A new key is stored through `KeySlotEditorState.StoreNewKey`: under a name that is valid and **not in use** (any case; the row says so and points to the list, and to File > Key manager for replacing), never while the stored keys cannot be listed (then it is not known whether the name is free), and from then on the slot names the key it made. The digits go through `KeyStorage.Store` into `KeyEntry` and `WindowsCredentialKeyProvider.Store`. The name of a new key has no live check (no green or red); the store button waits for a valid name and a key.
- The key is entered in a `KeyEntryBox`: hidden like a password until "Show key" is ticked; limited to the number of digits of the key (`MaxLength`, which follows the kind of key); and green on white for a key, black on red for anything else, as the key boxes of the task dialogs are, judged as a secret and never as a string. A shown key is in a text box and so in a string, which cannot be erased, as the typed keys of the task boxes are: the box starts hidden, hides again when it is cleared, and is cleared when a key was tried (stored, or refused by the vault) and when the window closes by any way (Close, Escape, the title bar), including the boxes of rows that were switched back. An entry that is not a key, a name in use and an unreadable list leave the digits in the box, so that the person can correct them. Enter in the box stores when a key can be stored; Close is not the default button, so Enter closes nothing and never loses digits that are not stored yet. No property of a view model holds a key (a test lists the string, `char[]` and `SecureString` properties), and no accessible name does.
- A row of the window builds the group for a key only when it is shown; a test that looks for the entry of a row that was never shown finds none.
- The names of the built-in key stores and their tooltips come from the resource files by id (`KeySlotProviderCatalog`); an extension keeps its own `DisplayName`, with a generic tooltip. The SDK is not changed for this: its surface is frozen by a snapshot, and a new member that old extensions do not export would hide them.
- The status of the connected application (`KeySupplierAvailability`: off, no supplier, connected) comes from `IKeySupplierStatus` (`BridgeKeySupplierStatus`, which asks the state of the bridge server through `ExternalControlService.AvailabilityOf`). A client that registers raises no event the window could use, so the window asks again once a second while it is open and stops when it closes.
- The texts are read once for each window (`CachedText`): the resources read the settings from disk at each lookup, and the status asks every second.
- Tooltips of the key controls are `ToolTip` elements with `KeySlotToolTipStyle`, which wraps at a maximum width (a tooltip given as plain text is one line and ran off the screen). WPF reads `ShowDuration` from the control that owns the tooltip; the property is inherited, so the editor and the window set it on their roots and a test asks each owner.
- Pictures: `RFIDGEAR_RENDER_DIR=<folder>` and the filter `rendered_to_pictures` make the tests of the windows, of the tabs and of the dialogs write PNG files (the windows in English and German; the tabs at 900x700, 1000x750 and 1200x750, typed and bound; the dialogs at their smallest and default size, bound; both in the language of the settings). Nothing is written without the variable. Look at them after a change of layout.

## The key manager of the menu
File > "Key manager..." (`OpenKeyManagerCommand`) opens `StoredKeysView`, a window that needs no project and no task: the keys that are stored in the Credential Manager under `RFiDGear/key/`, by name, with a way to store a key and to remove one. `StoredKeysViewModel` decides, `WpfStoredKeysLauncher` shows it as a modal window of the main window (`MainWindowViewModel.StoredKeysLauncher` is replaced in tests), and `WpfStoredKeysDialogs` asks the two questions with message boxes.

- The list is `WindowsCredentialKeyProvider.List()` over `ICredentialStore.Enumerate(prefix)`; the real one is `CredEnumerateW` with the filter `RFiDGear/key/*`. Only the target names are copied out and no secret is read (the tests check that no read reaches the vault). CredEnumerate returns whole credentials, secrets included, in memory that CredFree gives back without erasing it, so `NativeCredentialStore.ZeroBlobs` erases every returned blob first, also when reading a name fails (a test lays out such a listing in unmanaged memory and checks the bytes). The provider checks the answer again (the prefix, and `SecureKeySyntax.IsValidReference`), so a vault that ignores its filter, or a credential that was stored by hand under a name that is not a reference, is not listed. NOT_FOUND is an empty list; any other error is shown as an error and never as "no key is stored".
- Storing goes through `KeyStorage.Store`, the one place where the digits of an entry become a key (the key manager of a task uses it too), and the digits are entered in a `KeyEntryBox` as in the key manager of a task (hidden, "Show key", limited, coloured, store button waiting for a key). The view model asks first when the name is in use (it lists again right before, because another program may have changed the vault) and stores nothing while the list cannot be read, and `StoreEntered` answers whether a key was tried: the window clears the box then, and keeps the digits when nothing was stored (the name is not valid, the entry is not a key, the list could not be read, or the person said No to the replacement), so that the person can go on. The name box has no live check. A key that is removed is asked about too; a key that is gone already counts as removed.
- The window always shows the status of the connected application, like the key manager of a task does when a slot uses it. Texts are read once (`CachedText`), tooltips wrap (`KeySlotToolTipStyle`), the box is cleared when the window closes, Enter stores and closes nothing, and no property of a view model holds a key (a test lists the text properties).
- A new `ICredentialStore` needs `Enumerate` as well; `FakeCredentialStore` has `EnumerateError` and `EnumerateIgnoresPrefix` for the cases above.

## Moving the keys of an existing project into the Credential Manager
File > "Move keys of a project to the Credential Manager..." takes a project whose tasks have their keys typed in, stores each key in the Credential Manager and saves a new project that names the keys instead. The project it starts from is only read, and a file is never overwritten.

- `KeyMigration` is the engine, `KeyMigrationFlow` the dialogs (behind `IKeyMigrationDialogs`, so the flow is tested with a person that answers as told). The files of a run go through `IKeyMigrationProjects`; the real one, `DatabaseKeyMigrationProjects`, has a `ProjectManager` with a temporary folder of its own, because creating a `DatabaseReaderWriter` deletes `*.tmp`, `taskdatabase.xml` and `*.rfprj` in the root of its `ProjectManager` and must not do that to the profile of the running application.
- The steps: read the project; collect the typed keys of every task through `IKeyMigrationHost` (`EmbeddedKeySlots` lists the slots the task would write to the project, so a copy that the task only keeps for its own convenience is not moved); store each different key once under a random reference (`migrated/<16 hex digits>`; a slot with the same key shares the credential; a reference that is taken is never overwritten) and read it back; bind the slots in memory; write the new project; read it again.
- A project of a newer version is refused (`IsSupportedVersion`, as in `ProjectHostImpl`): it would be written again without the parts this version does not know. The source is hashed before and after it is read.
- The new project is created, never replaced: `WriteDatabase(..., replaceExisting: false)` puts it in place with a move that fails when a file exists, also one that appeared after the check. It has to pass the check: no key in its text (as written, and as pairs separated by a space), every slot bound to the reference of the run, no key typed into a bound slot, and every reference gives the key of its slot. If a step fails, or the person cancels, the credentials the run stored are removed and the new project is deleted. A run never removes a credential it did not store. What could not be removed is in the report (`UnremovedReferences`, `UndeletedTarget`) and the dialog names it; "nothing is left" is said only when it is true.
- A typed value that is not a key of the length its slot needs (the setters of a task accept anything) is not moved. It is reported and stays in the new project as it was typed.
- Deleting the old project is a second, separate question. `DeleteOriginalAsync` reads the original and the new project again and compares the key the original holds for each moved slot, byte for byte, with what the reference of the new project resolves to (every slot has to name the Credential Manager), because the person may have changed a credential since, also to another key of the same length. It deletes nothing for a failed run, when both reports name the same file, or when the original is no longer the file that was read (its hash, looked at last, right before the delete; a few milliseconds remain between that look and the delete).
- `KeyMigrationReport` has task numbers, slot ids, references, counts and paths, and no key; it is what the person sees and what the logs may hold. The logs of the run have the type of an exception and never its message.
- A project is now written straight into its archive. An earlier version wrote `taskdatabase.xml` into `%LocalAppData%\RFiDGear\` first and zipped that copy; it held every typed key in plain text. A `DatabaseReaderWriter` removes that file from the folder when it is created.

## Hardware cases for the secure key provider
`RFiDGear.HIL.Tests/SecureKeyWorkflowTests` runs bound DESFire tasks on a real card (the reserved test application, AES and DES). They are gated by the setting `secureKeys` in `hil.settings.json`, which is off in the sample, because they change a key on the card and put test credentials into the user's Credential Manager. `SECURE-KEYS.md` next to them lists the cases, the checklist for what needs a person (the PICC master key, a card pulled during a key change, MIFARE Classic and MAD, saving during a run, automatic mode, Format card, the migration) and how to clean up after an interrupted run.

- A setting has to be added in two places: `HilSettings` (the tests) and `Run-HilTests.ps1`, which reads the file with a parser of its own and refuses a name it does not know. `HilSettingsTests` fails when they drift apart.
- The cases have a fixture and a collection of their own (`HilSecureKeyFixture`, `HILSecureKeys`), because xunit creates the fixture of a collection also when every test in it is skipped. `HilFixture` would open the reader and delete the test application from the card then, even with `secureKeys` off. The gate does nothing at all unless the setting asks for it (`HilSecureKeyFixtureTests`); the collections of the project run one after the other.
- The HIL project sees the internals of the host (`InternalsVisibleTo`), so that the cases store their test keys with `WindowsCredentialKeyProvider.Store`, the code the application uses. `HilVault` keeps what it stored under `hil/<run>/...` and removes exactly that when it is disposed.
- The keys typed into a bound slot are decoys on purpose: they are the ones the card would accept where the vault key is refused, or the other way round, so a task that used the typed key could not pass.
- `HilSecureKeyScenarioSelfCheckTests` runs the same task builders and the same vault helper against a scripted reader and a dictionary, so a mistake in the set-up of a case shows up without a card.

## Ultralight, Ultralight C, EV1 and NTAG: facts that bite
One task kind (`MifareUltralightSetupViewModel`) reads and writes the pages of the chips of the Type 2 family; `CLAUDE.md` has the shape of it, `RFiDGear.HIL.Tests/ULTRALIGHT.md` the hardware cases. What to know before you change it:

- **The layout is a table, and a chip that is not in it is refused.** `UltralightMemoryMap` has one row per chip (pages, user pages, readable pages, protected pages) and the tests pin every row. The reader finds the chip (Elatec: GET_VERSION and the sub type; PC/SC: the name LibLogicalAccess gives it), looks it up and refuses a (type, size) it does not know. Never guess a layout from a neighbour: an NTAG210, 211, 212 and 214 have none yet.
- **A READ returns four pages and wraps to page 0**, also on the Elatec reader (probed on an NTAG215: 16 bytes, and past the last page it goes on at page 0). The engines read one page per READ and slice, and never ask beyond the table. The key pages of an Ultralight C (44 to 47) cannot be read at all, so `ReadablePageCount` is 44 and a read that reaches them is refused; the password and the PACK of an EV1 and an NTAG read as zeros, so a write verify does not compare them.
- **A refused call on the Elatec reader looks like a missing card.** A read returns `null` without an exception, a write and an authentication throw `ReaderException` with the text "error AccessDenied", `ErrorNumber` is always `None` (Elatec.NET's constructors that set it are not used at its throw sites), and after any refusal the chip is idle until it is selected again. The call being made decides what a refusal means (a password failure is `AuthFailure`, a page refused is `PermissionDenied`), and one read-only look at the antenna after a `null` tells a refusal from a card that was taken away. The text of the exception is parsed with a closed table and never trusted beyond that.
- **Elatec.NET reports NTAG and EV1 chips since 0.7.0-beta.2** (the sub types 0xA0 to 0xA6 and 0x92 to 0x94); it still reports an Ultralight C as a plain Ultralight, so the expectation of the task decides between the two. `CARD_TYPE` is stored in projects by name, and the renamed values go through the table in `NormalizeLegacyProjectXml`.
- **The family of a chip type is taken from the high byte, as an int.** The application is built with overflow checks, and `(short)type` throws for every type from 0x8000 up (an Ultralight is 0x9000, an NTAG 0xA000 and up). `UltralightChipTypes` has the one place that says what is of the family.
- **PC/SC knows only the plain Ultralight and the C** (LibLogicalAccess 3.7.0): an NTAG215 comes back as a generic chip of the type "unsupported unknown", with no commands and no adapter, so there is no raw channel to fall back on either. An EV1 or an NTAG on a PC/SC reader is a protocol constraint and nothing is sent. A task asks `ReaderDevice.SupportsUltralightAccess` before it asks a key provider for anything, so a vault that is down does not turn a known refusal into a missing key. Every PC/SC operation, `ReadChipPublic` included, goes through one session gate.
- **Keys are the secure key slots** (`SecureKeySlots.Ultralight`): the key of a C is one slot (`TripleDes2K`), the password (4 bytes) and the PACK (2 bytes) are two (`SecureKeyAlgorithm.UltralightPassword`, `UltralightPack`, an additive change of the contract that re-baselined its snapshot). The bridge's key provider has no wire name for them and answers no key, so the task ends `KeyUnavailable`. The byte order of the C key is not verified on a card for either reader, and no key is offered as a default. Never send the factory password `FFFFFFFF` of an NTAG to a card: a failed try counts against AUTHLIM.
- **A write is checked before the keys and again by the reader.** The same code (`UltralightRequest`) answers both: the data is whole pages of hexadecimal digits, the pages are in range for the chip the task names, pages 0 to 3 and the lock, configuration, password and key pages need the opt-in **and** a named chip, and the authentication has to be one that the chip has. The reader checks again against the chip it finds, and that one counts. A multi-page write has no rollback: `FailedPage` says where it stopped.
- **One operation per task at a time.** `RunPageOperationAsync` is guarded by a flag for the whole operation, the wait for the keys included; a second call returns without touching the outcome. While one runs the buttons that run the task, OK and Cancel are off and the window does not close (a write that waits for its key would reach the card after the dialog is gone, whichever button closed it).
- **The grid of the dialog is a view of the task.** `PageRows` are made from `WriteDataHex` (or, for a read, from the pages asked for and the bytes of the last read) and are no part of the project. While a row is not a whole page the data is the rows after a vertical bar (`|A1B2|C3D4`), which `UltralightPayload.TryParse` refuses, so rows shown apart are never joined to a page the grid does not show and an empty row does not move the next one up. The boxes of the first page and of the number of pages keep their text (`StartPageText`, `PageCountText`): WPF leaves the number of the task as it was when a box holds no number, so the buttons are off and a run is refused while a box holds no page of a chip (0 to 230) or no number of pages (0 to 231). The number of a row is the first page plus its place, and the application is built with overflow checks: that arithmetic is `unchecked`, or a first page near `int.MaxValue` stops the grid.
- **The dialog that edits a task copies its properties by reflection**, and an exception in one setter ends the copy at that property, silently (the constructor logs it): everything declared behind it stays at its default. The `Items` setter threw for the plugins that an edited task never composed, so the dialog of an existing Ultralight task opened empty. The DESFire dialog skips that property by its type; the Ultralight dialog skips the plugin properties by name and logs a property that fails and goes on. The Classic dialog has the same loop, and it does not stop at that property there. A probe (give every simple property of a Classic task a value of its own, then open the dialog on it) found 45 of 55 copied and 10 not: the target keys (`ClassicKeyAKeyTarget`, `ClassicKeyBKeyTarget`), the four MAD keys and `SelectedMADSector` come out as their defaults. Whether that is intended, or loses a key when the person presses OK, was not looked into.
- **A test of a command that checks a reader answer sets `Connected`.** The test reader of the key tests (`KeyRecordingReader`) is connected only when told so (`Connected = true`), as the host checks the connection of every reader but a PC/SC one before it asks for a key.

## MIFARE SAM AV3 setup: facts that bite
The window under Tools (`SamSetupView`) and the steps behind it (`Services/Sam`) set up a MIFARE SAM AV3 in a PC/SC reader; `CLAUDE.md` has the shape of it and `RFiDGear.HIL.Tests/SAM-AV3.md` the hardware checklist. What to know before you change it:

- **LibLogicalAccess is the transport and nothing else.** It names the SAM (`SAM_AV3`, with an AV2 command class that this code does not use: the host protocol is `Elatec.NET.Sam.SamAv3HostSession`, which has NXP's known-answer tests). The raw channel is `getDefaultReaderCardAdapter().getDataTransport().sendCommand(ByteVector, ms)`; the SWIG wrapper hands back the base types, so a cast to `ISO7816ReaderCardAdapter` is `null`. `adapter.sendCommand` runs a result checker and throws a `CardException` for every status word but `9000`, which breaks the three-pass authentication (`90AF`) and the "never activated" answer (`6985`): do not use it. Not `winscard.dll` either: that was the maintainer's choice.
- **`connect()` opens the card; the ATR does not need it.** `connectToReader()` and `waitInsertion()` are enough for `getATR()` and `getSingleChip()` (probed: `isConnected()` stays false), and `connect()` lets the library identify the chip on its own. The search over all readers therefore reads ATRs only (`ISamReaderSource.ReadAtr`), and `Open` connects to a card that was shown to be a SAM. The virtual reader `Windows Hello for Business` holds a made-up card and is never touched.
- **The bench SAM** (HID OMNIKEY 5422, contact slot): ATR `3BDF18FF81F1FE43003F07834D49464152452053414D204156333011` (T=1, historical bytes "MIFARE SAM AV30"); SAM_GetVersion `80 60 00 00 00` answers 31 bytes and `9000` with hardware information `04 01 01 05 00 23 01` and software information `04 01 01 05 01 1F 01` first; an unknown instruction (`80 FF 00 00 00`) answers `6D00` through the data transport. The serial number is in the rest of the version answer and never leaves `SamDetection`.
- **The trace of LibLogicalAccess is not under our control.** With `config.log.enabled` and `seecommunication` the library writes every answer in hexadecimal to its own log, and the answer to SAM_GetVersion holds the serial number of the SAM before `SamDetection` drops it. That trace is off unless somebody switches it on; nothing in RFiDGear redacts it, so the claim that the serial number reaches no log is about the logs of RFiDGear. `SAM-AV3.md` tells the person who runs the checklist to leave it off.
- **The reader units of the library hold only a weak reference to their provider** (and with it the PC/SC context). `LlaSamReaderSource` keeps the provider in a local with `GC.KeepAlive` after the last call on the unit, and a connection keeps it for as long as it lives. `LibLogicalAccessProvider` keeps it in a field for the same reason.
- **A new SAM answers SAM_AuthenticateHost with `6985`** (not activated), at the first command and before a key is used; that is what tells the dialog to offer the activation (verified on a real SAM). After the activation the same part 1 answers `90AF` and a 12-byte random number. **Part 1 leaves the SAM waiting for part 2:** a real authentication that follows it is answered `6700` (wrong length), so never send part 1 as a probe right before an authentication on the same SAM (the window does not; it asks SAM_GetVersion only). A wrong key in a later part would count as a use of the key if a usage counter were linked to the entry; the master entry of the bench SAM has none.
- **The activation worked on a real SAM AV3 and persists.** SAM_LockUnlock with P1 `03`, key entry 0, version 0, the factory key, three passes (the frame was taken from an AV2 library) answered `90AF` (12-byte random number), `90AF`, `9000` with a 16-byte proof that the library checks (2026-11-15). Before and after only the last byte of the SAM_GetVersion answer changed, `03` to `A3` (bits `0x80` and `0x20`; what they mean is not known), and part 1 went from `6985` to `90AF`. After the SAM was taken out and put back it was still activated. No way back was found and none was tried, so it is treated as irreversible. The word "activate" is NXP's for the AV3 (the AV2 data sheet speaks of a switch from AV1 to AV2 mode; nothing we saw says that this is that). If the SAM answers the last command with success but the proof is wrong, the SAM may be activated all the same (`MayHaveTakenEffect`: the connection is closed, check, then authenticate).
- **A blank key entry is disabled, and a write has to enable it** (verified on a real SAM, 2026-11-15; NXP AN12701, table 2, page 15, read by the maintainer): SET bit 9 (`0x0200`) is "disable key entry". A never-written entry reads back with SET `0x0220`; the entry that the setup writes has SET `0x0020`, so bit 9 is clear and the entry is enabled (the master entry is `0x0020` too). SET `0x0020` says AES-128 (bits 3 to 5 are `100b`) and **nothing about what the key is for: that is the key class in the low bits of ExtSET** (`001b` PICC, `000b` host). So "usable to authenticate a PICC" is three things together: bit 9 clear, type AES-128, class PICC. The setup reads the entry back after a write (`ReadBackAsync`) and says so; `SamKeyEntryInfo.Verdict` is the one place that decides.
- **SAM_GetKeyEntry** is `80 64 <entry> 00 00` under the secure session (`SamAv3HostSession.ExecuteSecureAsync(0x64, entry, 0x00, null, 0x00)`), answers `9000` and 13 bytes: key versions A, B, C (3) | DF_AID (3) | DF_KeyNo | KeyNoCEK | KeyVCEK | RefNoKUC | SET (2, low byte first) | ExtSET. The order is inferred from three distinctive values that were written (`FF`, `0x0020`, `0x01`), not from a published table of the answer. It holds no key. A plain command inside an authenticated session is refused (SAM_GetVersion answered `6A84` right after a write), so the read-back goes through the same session.
- **The master entry of a new SAM** reads back as SET `0x0020`, ExtSET `00`, RefNoKUC `FF`: no key usage counter (wrong keys count against nothing), SET bit 10 clear (no SAM_LockUnlock after a reset: the activation survived a removal of the SAM), SET bit 8 clear (and host authentication works, so that bit is not what lets the master key authenticate).
- **The written key is a PICC key** (`SamAv3KeyEntry.CreateAes128PiccKey`: SET `0x0020`, ExtSET `0x01`). The SAM accepted it (`9000`, CMAC checked) and reads it back as written: enabled, AES-128, PICC class. A host authentication cannot prove it (it is no host key) and a key cannot be read back, so the read-back proves the entry; that the key is the typed one was proved on 2026-11-16: the typed key authenticated a DESFire EV3 whose master key SAM_ChangeKeyPICC had set from this entry. **It needs Keep IV to authenticate a DESFire card through the SAM:** a DESFire AES key needs SET `0x0024` (b2 "Keep IV"; NXP AN12696, table 1), and the helper `CreateAes128PiccKey` of Elatec.NET writes `0x0020`, so part 2 of SAM_AuthenticatePICC answers `901E` (verified: rewritten with `0x0024` it works). The setup writes the entry through `SamKeyEntries.Aes128PiccKey` (SET `0x0024`), and the read-back says "Keep IV is not set" (`SamKeyEntryCheck.MissingKeepIv`) for an enabled AES-128 PICC entry without it. **An entry that an older build wrote has `0x0020` and has to be written again.** A native DES key of a card is SET `0x0000`, and Elatec.NET cannot write it (AES-128 entries only): the frame is built by us, see the record. The wrapper `Av3HostSession` never lifts `allowMasterKeyChange` or `allowIrreversibleLock`.
- **A native TDEA key (DES or 2K3DES, 16 bytes) is written by our own frame:** Elatec.NET's `ChangeKeyEntryAsync` throws `NotSupportedException` for anything but an AES-128 entry, before it sends SAM_ChangeKeyEntry. `SamKeyEntryFrame` builds the data field (key A, B, C as three copies of the key | DF_AID (3) | DF_KeyNo | KeyNoCEK | KeyVCEK | RefNoKUC | SET (2, low byte first) | version A, B, C (all three the key version, as the library does) | ExtSET; INS `C1`, P1 the entry, P2 `FF`, no Le) and `Av3HostSession.WriteNativeKeyEntryAsync` sends it through `ExecuteSecureAsync`, which has none of the library's guards: the method itself allows only the entries 1 to 127, and the settings (SET `0x0000`, ExtSET `0x01`, no key usage counter) are constants, never a caller's. `SamKeyEntryFrameTests` compares the layout with the frame of the library for an AES entry (the session is built by reflection on internal types of the package: if a new version of Elatec.NET moves them, that test says so). SET key type `000b` is native TDEA and needs Keep IV clear; AES-128 (`100b`) needs it set (NXP AN12696, table 1): `SamKeyEntryInfo.VerdictFor(kind)` checks that.
- **A PICC authentication through the SAM leaves state on both sides.** The SAM that has had a part 1 and no part 2 answers the next part 1 with `6700` (it takes the data for a part 2); `SAM_KillAuthentication` for the PICC authentication is `80 CA 01 00` with **no Le** (with one: `6700`, or `6883` while an authentication is pending). A card that was left with an unfinished authentication answers the next command with `91CA` and is clean afterwards. Closing the connection to the SAM resets it, so a new connection starts clean. `SamPiccSession` kills first, kills again after a part 1 that was not finished, and sends the SelectApplication once more after a `91CA`; nothing else is ever sent twice. Opening the SAM takes about 120 ms (ReadAtr and connect), so it is opened per operation under `SamPortGate`. All seen on a real SAM: `SAM-PICC-FIRST-CONTACT.md`.
- **The default reader unit of the PC/SC provider is the first reader, and on a reader pair that is the contact slot with the SAM in it.** `InitializeReaderProvider` fell back to `readerProvider.createReaderUnit()` when no reader was chosen or the chosen one was gone. With the setting `SamReaderName` set, `PcscReaderChoice.Pick` returns "none" instead of that fallback, and never picks the SAM reader as the reader of the card (names compare without case and without the spaces around them); a unit that is bound to the SAM reader is dropped when the setting changes, first of all, so that a failing enumeration cannot keep it. The provider learns the reader of the card and the reader of the SAM together (`UpdateReaders`): one name after the other would choose a unit while the other name is not known yet, and a unit that exists is kept (`UpdateSelectedReader` alone does not switch it). The settings dialog gives an unconfirmed SAM reader only to a provider of its own: the provider of the application learns both when OK is pressed (also when only the reader or the provider changed), so a cancel leaves it as it was, and a card reader that was confirmed picks its unit again (`PcscReaderChoice.IsOtherReader`; the preview of the dialog keeps the unit it has). The box of the SAM readers is emptied and filled again with every change of the provider, and says "nothing" while it is empty: `SelectedSamReaderName` ignores that (`refillingSamReaders`), so the choice is still there when the items are back. The setting is saved only when the PC/SC provider is chosen, so that trying another provider does not lose it. An old `settings.xml` has no such element and reads as empty.
- **The first two sessions with a real SAM are written down** in `RFiDGear.HIL.Tests/SAM-AV3-FIRST-CONTACT.md`: every APDU and answer (the UIDs masked), the findings and what is still open. The second session is a DESFire EV3 through the SAM: the frames of SAM_AuthenticatePICC (INS `0A`) and SAM_ChangeKeyPICC (INS `C4`), the layout of the data field of SAM_ChangeKeyEntry, the key types in SET, and Keep IV. Read it before you change the frames or the read-back, and add to it: a finding must not live only in a pull request.
- **Whether LibLogicalAccess's disconnect resets the SAM is not known.** If it does not, an authenticated session stays in the SAM until it is reset or authenticated again; another program would need the session keys to use it, which only the closed window had.
- **The window holds the gate of the reader** (`SamSetupGate.RunExclusive`), because the host session is tied to the connection. A test that opens the main window view model must not rely on `IsReaderBusy` staying as it was: the launcher sets it.
- **A test double of the SAM cannot replay a recorded authentication:** `SamAv3HostSession` draws fresh random numbers. The tests script the session (`FakeHostSession`), or run the real session against a transport that answers `6985` (which needs no cryptography).
- **A key slot can name a key of the SAM** (provider id `sam`, reference `entry:version`, `SamKeyReference`), and it is deny-by-default: `KeyAcquisition.AcquireAsync` takes a `SamKeyPolicy` that is `Refuse` unless a command passes `AllOrNothing`, so Classic, Ultralight and every DESFire command that does not know the SAM end with `KeyUnavailable` before any card call when they use the slot (a slot that a command does not use is not asked for, from a provider or from the SAM: an Ultralight task without authentication has no key to get). The three suites of key resolution pin that with all slots bound and the vault untouched (`A_slot_bound_to_a_key_of_the_sam_stops_every_task_before_the_card_is_touched`). The reference is checked by `SecureKeySyntax.IsValidReferenceFor`, so a bad one is a broken binding, which stops the task even when its command does not use the slot (entry 0 is the master key of the SAM and is no reference). `SamKeyProvider` is built in only to reserve the id and to be listed, and hands out nothing. `SamKeySlots.Offered` says for which slots the key manager lists the SAM: the five slots of the authentication and of the key changes (the read and write keys of a file are not in it). A new command that takes keys of the SAM asks `AcquiredKeys.IsSam(slot)` and never calls `Hex` for such a slot (it throws).
- **The PC/SC relay (`LibLogicalAccessProvider.Sam.cs`) is one boundary per call.** It takes the session gate of the provider first (`ReadChipPublic` disconnects first, which would take the card away from a relay that is running), opens the SAM before anything else (`ISamPiccConnector`: the setting `SamReaderName`, never the reader of the card, only a card that says it is a SAM AV3, and nothing is sent to the card until that has happened), connects the card as a page operation does (`ConnectToAFreshChipAsync`) and checks that LibLogicalAccess calls it `DESFire*`, runs `SamPiccSession`, and lets go of both whatever happens (a failing release is only logged). The card is reached through `LlaApduTransport`, the data transport of LibLogicalAccess, never the adapter (which throws for every status word but `9000`). The errors a task sees: no SAM reader set, none found, busy, or the reader of the card is the SAM's: `KeyUnavailable` (not routed to the fallbacks of a project); a reader that fails, no card: `TransportError`; another card than a DESFire card, a key that a SAM entry cannot be (3K3DES): `ProtocolConstraint`; the TWN4 does not relay yet, so there the task ends `KeyUnavailable` before anything is sent (its operations answer `ProtocolConstraint`); the rest is the answer of the session. The tests (`LibLogicalAccessSamRelayTests`) replace the three seams that touch the native library (`CreateSamPiccConnector`, `OpenCardLinkForSamAsync`, `ReleaseCardLinkForSamAsync`) and set the SAM reader with `AssumeSamReader`; **a mutation that removes the release of the session gate makes the next call wait for ever**, so a mutation run of this class needs `--blame-hang-timeout`.
- **The DESFire commands that use keys of the SAM (`MifareDesfireSetupViewModel.Sam.cs`) branch right after the keys were acquired.** They ask with `SamPolicyOf(device)` (`AllOrNothing` for a reader that says `SupportsDesfireSamKeys`, otherwise `Refuse`), and when the key of the slot that authenticates is a key of the SAM (`keys.IsSam`) they hand the references to the reader and end: no pre-check authentication, no `TryUpdateKeyVersionAsync`, no `VerifyChangedApplicationKeyAsync` (the session authenticates again with the new key itself), and the typed key version is not used (the card gets the version of the SAM entry). The method `OnNewAuthenticateToCardApplicationCommand` is shared with the check tasks (`ReadAppSettings`, `CheckAppKeyCount`, `CheckFileSettings`): they pass `Refuse`, and a test runs them through the button. A new command that should use keys of the SAM does the same, and gets a case in `DesfireSamCommandTests` (the central one runs every task type with every slot bound to the SAM and a reader that can, and names the ones that may reach it). The key number that authenticates an application is the one of the change-key policy of the application (key 0 unless it says "change with the targeted key"), as for a typed key; `SAM-PICC.md` lists what has not been tried on a card (a key of an application other than the one that authenticated, AES to AES, AES to DES).

## Trying an extension in RFiDGear while you develop it
RFiDGear reads its extensions from `%ProgramData%\RFiDGear\Extensions` once, at start-up. After a build, the extension and the support libraries it needs (`RFiDGear.ExtensionLibraries.*`) can be copied there for you, so you only restart RFiDGear.

- **Off unless asked for**, because a build is not always your own: test runs, clean checkouts and tools that build modified code would otherwise put their output into a real RFiDGear. Turn it on with the value `true` in one of these (the command line beats the local file, which beats the environment):
  - `dotnet build RFiDGear.Extensions/CardCheckAssistant -c Debug -p:DeployExtensionsToRFiDGear=true`
  - `RFiDGear.Extensions/deploy.local.props` (not in the repository, and only seen by the checkout that holds it; a second clone or worktree needs its own), containing `<Project><PropertyGroup><DeployExtensionsToRFiDGear>true</DeployExtensionsToRFiDGear></PropertyGroup></Project>`
  - the environment variable `RFIDGEAR_DEPLOY_EXTENSIONS=true`. With a local props file present it cannot switch the step off again; use `-p:DeployExtensionsToRFiDGear=false` for that.
- Only the extension, its libraries and their symbols are copied; never the contract, the SDK or the host. The last build replaces what is there, even an older build from another checkout; files are skipped only when they are identical. Nothing is deleted.
- The extension is copied first. If it cannot be replaced (RFiDGear is running and holds it), that is a warning and nothing else is copied, so the folder keeps one older set that belongs together; the last message says the deploy is not complete. Close RFiDGear and build again. It is an error only if your build treats warnings as errors.
- The copy has the platform of the build: an x64 build does not load into an x86 RFiDGear and the other way round; an AnyCPU build loads into both. `-p:RFiDGearExtensionsFolder=<folder>` copies somewhere else.
- The database driver that the order store will need is not copied; nothing opens the order database yet.

## The external control bridge: facts that bite
`Services/ExternalControl` (the host side) and `RFiDGear.Bridge.Contracts` (what a client references) are described in `CLAUDE.md`; the protocol is `RFiDGear.Bridge.Contracts/README.md` and the guide for client authors `CLIENT-GUIDE.md`. What to know before you change either:

- **The contract is a promise.** `RFiDGear.Tests/ApiSurface/RFiDGear.Bridge.Contracts.api.approved` freezes the public surface (regenerate with `RFIDGEAR_UPDATE_API_SNAPSHOT=1` and `--filter "FullyQualifiedName~BridgeContractsApiSurface"`; a mutation run that changes the contracts must include `FullyQualifiedName~ApiSurface` in its filter), `BridgeSamples` + `BridgeGolden` hold one value of every message and its JSON. Every DTO property has an explicit `[JsonPropertyName]`; the host reads requests strictly (an unknown member is refused) and a client reads answers tolerantly, so a new request member needs a new capability that the client has seen.
- **`ExecuteAllAsync` has to START on the WPF dispatcher.** Admission is its synchronous prefix: a refusal is an already faulted task (`InvalidOperationException` is busy, `ArgumentException` a bad report variable), a pending task is an admitted run. The run id is chosen by the bridge through the internal `IPreassignedRunExecution`. The host raises its events synchronously on the thread that changed the state: a handler only numbers, queues and returns, and a thread-static marker (`MarkAdmitting`, `s_starting`) tells the bridge's own raise from somebody else's at the same moment.
- **Admission and the claim of a mode are compare-and-swap, not locks around calls.** The window's callback must move a request from pending to admitting before it asks the host; the 5 s wait must move it to abandoned before it answers `uiUnresponsive`; whichever wins is the truth, so "nothing was started" is never said about a run that starts late. A client's claim on automatic mode carries the controller's start number and is only valid while that number is the one that is running.
- **Order matters in three places, and each has a test.** The journal line `started` is written and flushed before the host is asked; `ended` before the result is final; the result of the run that stops automatic mode comes before the notice that it stopped. A session is disposed (the pipe closed) before the next pipe instance is created, because one instance is allowed and a stuck write would otherwise turn the bridge off for good.
- **Events are one FIFO of at most 64 durable notices per client.** State notices (running, reader, project) are merged, results and mode changes are not; a client that lets 64 wait is disconnected (the results stay in the log), and so is one that does not take a notice within 10 s. A test of the cap has to wait less than that watchdog, or it passes for the wrong reason.
- **StreamJsonRpc**: the library has no maximum message size (`CappedReadStream` ends the connection before it allocates); an unknown method and a parameter that does not fit both arrive as `RemoteMethodNotFoundException` (codes -32601 and -32602); the default `error.data` carries a stack trace, so `BridgeJsonRpc` and `BridgeFault` always answer with our own data and the host's trace source stays off; a client has to override `GetErrorDetailsDataType` or it loses our data. A call from the host to the client (`resolveKey`) passes the cancellation token on the wire.
- **Nothing a client sent is logged.** The bridge logs the type of an exception, never its text, and ids and numbers, never a variable, a path, a UID, a key or a reference. A key lives in a `SecureKeyLease` (pinned, zeroed on dispose); the base64 text in the JSON message cannot be erased, which the documentation says openly.
- **Tests that build a main window through the bridge** pass a temporary journal folder (`externalControlJournalDirectory`) and a unique pipe name; tests wait with a bound (`WaitAsync`, a deadline), never with a bare `await` on something a defect could stop completing, because a hang stops a mutation run for ever.

## Tests on xunit.v3
Both test projects (`RFiDGear.Tests` and `RFiDGear.HIL.Tests`) run on xunit.v3. xunit 2 is marked as legacy on NuGet (the whole `xunit` package, whatever its version), with `xunit.v3` as the replacement.

- **The package is `xunit.v3.mtp-off`, not `xunit.v3`.** The metapackage is built on Microsoft.Testing.Platform, and the .NET 10 SDK then refuses to run it through `dotnet test` ("Testing with VSTest target is no longer supported ... on .NET 10 SDK") unless `global.json` opts in to the new `dotnet test`, which has other filters (`--filter-method` and the like) and another trx logger. `mtp-off` is the same xunit.v3 without that platform, so `dotnet test`, `--filter "FullyQualifiedName~..."`, `--logger trx` and `Run-HilTests.ps1` work as before.
- **The test projects are executables** (`OutputType` Exe); the test assembly is the entry assembly of the process. Code that asks for the entry assembly gets the tests: `MefHelper` therefore scans its own assembly (`HostAssembly`), not the entry assembly, or the deliberately broken exports of `MefHelperLoadingTests` were composed into every container that a test builds (181 failures, all from that).
- **The process has to end by itself.** When a run is over, xunit.v3 starts a watchdog: a process that is still alive a second later prints "Waiting 10 seconds for foreground threads to exit", and one that is alive after ten forces the exit code 1, whatever the tests did (xunit 2 never saw this, the test host ended the process). The message guesses at a foreground thread; the cause can as well be slow exit handlers. It was one here: WPF's weak event table asks, at process exit, the dispatcher of every thread that used it to run a clean-up and waits for the answer, and a thread that has ended never answers. `DatabaseReaderWriter.ExecuteOnStaThread` made such a thread for every project that a test read (about half a second each), so it shuts down the dispatcher of its thread now (`DatabaseReaderWriterTests`). If a run is slow to end again, run `RFiDGear.Tests.exe -class <name>` for the classes and compare the total time with the time of the tests; then take a dump while the exit runs (`dotnet-dump collect --type Heap`, `clrstack` of the finalizer thread, which runs the exit handlers).
- **An exception that nobody observes is a fatal error of the run**, not a failure of the test that made it: an `async void` that throws, which is what `AsyncRelayCommand.Execute` does with a failed task unless the command is made with `AsyncRelayCommandOptions.FlowExceptionsToTaskScheduler` (`AsyncCommandBaseTests`).
- **A skip ends the test as a skip**: `Assert.Skip(reason)` and `SkipException.ForSkip(reason)` are reported as skipped, no longer as a failure with the message `$XunitDynamicSkip$`. `Assert.Throws` and `Record.Exception` do not catch a skip; a test of the skip itself catches the `SkipException` with `try`/`catch` (`HilSecureKeyFixtureTests`).
- **Changed signatures**: `IAsyncLifetime` returns `ValueTask`; `ITestOutputHelper` is in `Xunit`; `[TestCaseOrderer]` takes a type, and `ITestCaseOrderer` takes and returns an `IReadOnlyCollection` (`HilCaseOrderer`); a class that extends `FactAttribute` or `TheoryAttribute` takes the caller's file and line (`HilFactAttributes`, rule xUnit3003); the assembly attribute for "no parallelism" is `[assembly: Parallelization(Mode = ParallelMode.None)]`.
- **Analyzers**: the ones of xunit.v3 advise on tests that were written for xunit 2 (about 240 times `xUnit1051`, pass `TestContext.Current.CancellationToken`; also `xUnit2031`, `xUnit2029`, `xUnit1069`, `xUnit1073`). They are turned off for the unit tests in `RFiDGear.Tests.csproj` with a comment, and are a follow-up of their own.
