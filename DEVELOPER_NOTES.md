# Developer Notes

## One-attempt rule
Operations that change card state (authentication, file creation, key rotation, etc.) must only be attempted once per request. The provider layer should rely on the caller to orchestrate retries rather than automatically repeating failed calls. Automatic retries can leave a reader or card in an undefined state and mask the original failure reason. When a command fails, return the appropriate error code and let the orchestrator decide whether to re-run the task.

## Normalized provider error codes
The provider layer now returns a small, normalized set of error codes to make downstream handling consistent. These codes are surfaced by `ReaderDevice` and its implementations and should be propagated without collapsing distinct conditions into a generic catch-all:

- `AuthFailure`: authentication or key negotiation failed.
- `PermissionDenied`: access was explicitly refused by policy or configuration.
- `ProtocolConstraint`: the requested operation violated protocol constraints (e.g., resource already exists, limits exceeded).
- `TransportError`: communication problems such as unavailable readers or timeouts.
- `Unknown`: unexpected state or unclassified errors that do not map to the categories above.
- `KeyUnavailable` (set by a task command, not by a reader): a key slot is bound to a secure key provider and the key could not be obtained. The command made no card call and used no other key.

When you add or update provider logic, choose the most specific code that matches the condition so that calling layers can react accurately (e.g., prompting for different credentials versus retrying the connection).

## The Windows Credential Manager as a secure key provider
RFiDGear brings one secure key provider of its own, `windows-credential-manager` (`WindowsCredentialKeyProvider`). A task slot that is bound to it holds a reference instead of a key, and the key is read from the Credential Manager when the task runs.

- The id is stored in project files and never changes. Extensions cannot take it over.
- A reference is the name of a generic credential below the fixed prefix `RFiDGear/key/`. Whatever a project says, the name that reaches the vault starts with that prefix, so a project cannot read the credential of another application.
- The credential holds the hexadecimal digits of the key as UTF-16 text, which is how `cmdkey` stores a password: 12 digits for a MIFARE Classic key, 32 for a DES or AES key, 48 for a 3K3DES key. Without a tool of ours, a key is stored with `cmdkey /generic:RFiDGear/key/<reference> /user:RFiDGear /pass`, which asks for the digits at a prompt. Do not write them on the command line (`/pass:<digits>`): other programs can read a command line, and shell histories and process logs keep it. The prompt reads from the console, so a test cannot drive it; a test stores a dummy value with `/pass:<digits>` to pin the format that the tool writes, and reads it back.
- What it protects against is a key that ends up in a project file, a backup or an e-mail. It does not protect against a program that runs as the same user: the Credential Manager gives the secret to every process of that user.
- The conversion from the stored text to the key works on the bytes and never makes a string, because a string cannot be erased. The copies of the secret that the vault hands out are erased, and the arrays that hold one are on the pinned object heap, so the garbage collector never leaves an old copy behind.
- `ICredentialStore` is the seam in front of the vault. The tests use a dictionary; one test uses the real vault with a name of its own and removes it.

## Key slot editors and the key manager in the task dialogs
Every box in which a card key is typed is wrapped by `KeySlotEditor` (`Views/KeySlotEditor.xaml`): the sixteen key boxes of the DESFire card mastering, application mastering and data explorer tabs and of the MIFARE Classic key tab. The wrapper shows that a slot names its key by a reference to a secure key provider instead of holding it typed. The choice itself is made in the key manager (next section), which a button at the bottom of each section of keys opens.

```xml
<ctl:KeySlotEditor Grid.Row="0" Grid.Column="1" Host="{Binding}" SlotId="desfire.read">
    <TextBox Text="{Binding DesfireReadKeyCurrent, UpdateSourceTrigger=PropertyChanged, Mode=TwoWay}" ... />
</ctl:KeySlotEditor>
```

- The wrapped box keeps everything it had: its style, its tool tip, its validity colours, its `MaxLength`. Only the grid placement and the `Visibility` move to the wrapper. `SlotId` is an id of `SecureKeySlots`; `Host` is the task and has to implement `IKeySlotHost`, which both setup view models do.
- What a slot decides is in `KeySlotEditorState`, with the question to the person behind `IKeySlotEditorDialogs` (only `ConfirmReplaceKey`), so that it is tested without a window. Switching a slot that holds a key to a reference asks first (a slot without a key is switched without a question). The binding is written first and the key is cleared second, so the slot is never left with neither. The state has no window of its own any more; the editor and the key manager both show it.
- While a slot is bound, the wrapped box is disabled and covered by a plain grey field (`ReferenceCover`, over exactly the box): an empty box would show the red of an invalid key. Below the box a line says `Reference: <name>`, and its tooltip adds the key store. A slot with a typed key has no such line and no height for it, so it looks as it always did. The line is a `LineWithoutWidth`, a frame that takes the width of the box and asks for none: the data explorer has columns that are as wide as their content, and a long name must not make them grow.
- The caption of a slot uses the margins of the wrapped box (`CaptionMargin`, `CoverMargin`), so the line and the cover sit where the box does. They are read when the box arrives, not copied as numbers.
- A section of keys has a `KeyManagerButton` at the bottom of its group box, with the height, the padding and the margins of the buttons around it. It is not bound to a list of slots: it looks for the visible `KeySlotEditor`s in its nearest `GroupBox`, in screen order, so `desfire.app.old` is in the manager only while its box is shown. Without the button a visible, bound key would have no way to be changed back, which is why the editor has no button of its own.
- While the keys of a command are obtained from their providers (`IsFetchingKeys`), the tabs of the dialog take no input (`AreInputsEnabled`): what a person changes meanwhile would no longer be what the keys were asked for.
- A new key box needs the wrapper, a slot id, a name for the slot (`keySlotName...` in both resource files, mapped in `KeySlotNames`; a test fails for a slot without one), and a `KeyManagerButton` in its section. `KeySlotEditorViewTests` lists the slots of every tab and fails when a key has no editor, and sweeps every task type of the DESFire and Classic tabs: every visible editor has a visible, enabled button in its own group box.
- A tab has less room in its dialog than alone in a window: the task above it and the status below it take their part, and the tab gets about three quarters of what the window gains in height. The tests therefore also show the real dialogs, at the smallest size each declares (`MinWidth`, `MinHeight`) and at the default, for every task type, typed and bound, and fail when a manager button or a caption ends below the group box of its section (the space the part keeps below it counts) or the group box below the area of the tab. The button of the right-hand group of the DESFire application mastering tab needed the minimum and the default height of the DESFire dialog to go from 700 and 750 to 760, and the data explorer (whose right-hand group was already wider than the dialog at 900) the minimum width to go from 900 to 990. If a section grows again, raise the size rather than let the button, the only way back from a reference, be cut off.
- In the Classic key tab, WPF clamps an out-of-range `Grid.Row` to the last row. The sub-boxes of the MAD sections have to name their row (`Grid.Row="2"`) before a row is appended to their grid, or they move down with it.
- `x:Static` cannot reach a constant of an internal class: such a value is set in the code-behind.

## The key manager
`KeyManagerView` (`Views/KeyManagerView.xaml`) is a modal window that the button opens with the task dialog as its owner; `KeyManagerViewModel` has one `KeyManagerSlotRow` for each slot, and each row is a thin face on a `KeySlotEditorState`. Nothing is staged: a choice is written to the task at once, and the task dialog drops its copy when it is cancelled, so the window has a Close button and no OK and Cancel. `IKeyManagerLauncher` (`WpfKeyManagerLauncher`) shows it, so the view models do not know a window.

- A row says "Use reference" or "Use typed key". With a reference, it has the key store, the name, and for the Credential Manager an inline password box and "Store key". The digits go through `KeySlotEditorState.StoreEntered(SecureString)` into `KeyEntry` and `WindowsCredentialKeyProvider.Store`, the box is cleared whatever came of it, and again when the window closes by any way (Close, Escape, the title bar), including the boxes of collapsed rows. Enter in the box stores; Close is not the default button, so Enter closes nothing and never loses digits that are not stored yet. No property of a view model holds a key (a test lists the string, `char[]` and `SecureString` properties), and no accessible name does.
- The names of the built-in key stores and their tooltips come from the resource files by id (`KeySlotProviderCatalog`); an extension keeps its own `DisplayName`, with a generic tooltip. The SDK is not changed for this: its surface is frozen by a snapshot, and a new member that old extensions do not export would hide them.
- The status of the connected application (`KeySupplierAvailability`: off, no supplier, connected) comes from `IKeySupplierStatus` (`BridgeKeySupplierStatus`, which asks the state of the bridge server through `ExternalControlService.AvailabilityOf`). A client that registers raises no event the window could use, so the window asks again once a second while it is open and stops when it closes.
- The texts are read once for each window (`CachedText`): the resources read the settings from disk at each lookup, and the status asks every second.
- Tooltips of the key controls are `ToolTip` elements with `KeySlotToolTipStyle`, which wraps at a maximum width (a tooltip given as plain text is one line and ran off the screen). WPF reads `ShowDuration` from the control that owns the tooltip; the property is inherited, so the editor and the window set it on their roots and a test asks each owner.
- Pictures: `RFIDGEAR_RENDER_DIR=<folder>` and the filter `rendered_to_pictures` make the tests of the window, of the tabs and of the dialogs write PNG files (the window in English and German; the tabs at 900x700, 1000x750 and 1200x750, typed and bound; the dialogs at their smallest and default size, bound; both in the language of the settings). Nothing is written without the variable. Look at them after a change of layout.

## The key manager of the menu
File > "Key manager..." (`OpenKeyManagerCommand`) opens `StoredKeysView`, a window that needs no project and no task: the keys that are stored in the Credential Manager under `RFiDGear/key/`, by name, with a way to store a key and to remove one. `StoredKeysViewModel` decides, `WpfStoredKeysLauncher` shows it as a modal window of the main window (`MainWindowViewModel.StoredKeysLauncher` is replaced in tests), and `WpfStoredKeysDialogs` asks the two questions with message boxes.

- The list is `WindowsCredentialKeyProvider.List()` over `ICredentialStore.Enumerate(prefix)`; the real one is `CredEnumerateW` with the filter `RFiDGear/key/*`. Only the target names are read: the pointer to the secret in the structure is never followed, and the tests check that no read reaches the vault. The provider checks the answer again (the prefix, and `SecureKeySyntax.IsValidReference`), so a vault that ignores its filter, or a credential that was stored by hand under a name that is not a reference, is not listed. NOT_FOUND is an empty list; any other error is shown as an error and never as "no key is stored".
- Storing goes through `KeyStorage.Store`, the one place where the digits of an entry become a key (the editors of the task dialogs use it too). The view model asks first when the name is in use (it lists again right before, because another program may have changed the vault), and `StoreEntered` answers whether storing was tried: the window clears the box then, and keeps the digits when nothing was tried (the name is not valid, or the person said No to the replacement), so that the person can go on. A key that is removed is asked about too; a key that is gone already counts as removed.
- The window always shows the status of the connected application, like the key manager of a task does when a slot uses it. Texts are read once (`CachedText`), tooltips wrap (`KeySlotToolTipStyle`), the box is cleared when the window closes, Enter stores and closes nothing, and no property of a view model holds a key (a test lists the text properties).
- A new `ICredentialStore` needs `Enumerate` as well; `FakeCredentialStore` has `EnumerateError` and `EnumerateIgnoresPrefix` for the cases above.

## Moving the keys of an existing project into the Credential Manager
File > "Move keys of a project to the Credential Manager..." takes a project whose tasks have their keys typed in, stores each key in the Credential Manager and saves a new project that names the keys instead. The project it starts from is only read, and a file is never overwritten.

- `KeyMigration` is the engine, `KeyMigrationFlow` the dialogs (behind `IKeyMigrationDialogs`, so the flow is tested with a person that answers as told). The files of a run go through `IKeyMigrationProjects`; the real one, `DatabaseKeyMigrationProjects`, has a `ProjectManager` with a temporary folder of its own, because creating a `DatabaseReaderWriter` deletes `*.tmp`, `taskdatabase.xml` and `*.rfprj` in the root of its `ProjectManager` and must not do that to the profile of the running application.
- The steps: read the project; collect the typed keys of every task through `IKeyMigrationHost` (`EmbeddedKeySlots` lists the slots the task would write to the project, so a copy that the task only keeps for its own convenience is not moved); store each different key once under a random reference (`migrated/<16 hex digits>`; a slot with the same key shares the credential; a reference that is taken is never overwritten) and read it back; bind the slots in memory; write the new project; read it again.
- A project of a newer version is refused (`IsSupportedVersion`, as in `ProjectHostImpl`): it would be written again without the parts this version does not know. The source is hashed before and after it is read.
- The new project is created, never replaced: `WriteDatabase(..., replaceExisting: false)` puts it in place with a move that fails when a file exists, also one that appeared after the check. It has to pass the check: no key in its text (as written, and as pairs separated by a space), every slot bound to the reference of the run, no key typed into a bound slot, and every reference gives the key of its slot. If a step fails, or the person cancels, the credentials the run stored are removed and the new project is deleted. A run never removes a credential it did not store. What could not be removed is in the report (`UnremovedReferences`, `UndeletedTarget`) and the dialog names it; "nothing is left" is said only when it is true.
- A typed value that is not a key of the length its slot needs (the setters of a task accept anything) is not moved. It is reported and stays in the new project as it was typed.
- Deleting the old project is a second, separate question. `DeleteOriginalAsync` reads the original and the new project again and compares the key the original holds for each moved slot, byte for byte, with what the reference of the new project resolves to (every slot has to name the Credential Manager), because the person may have changed a credential since, also to another key of the same length. It deletes nothing for a failed run, when both reports name the same file, or when the original is no longer the file that was read (its hash, looked at last, right before the delete; a few milliseconds remain between that look and the delete).
- `KeyMigrationReport` has task numbers, slot ids, references, counts and paths, and no key; it is what the person sees and what the logs may hold. The logs of the run have the type of an exception and never its message.
- A project is now written straight into its archive. An earlier version wrote `taskdatabase.xml` into `%LocalAppData%\RFiDGear\` first and zipped that copy; it held every typed key in plain text. A `DatabaseReaderWriter` removes that file from the folder when it is created.

## Hardware cases for the secure key provider
`RFiDGear.HIL.Tests/SecureKeyWorkflowTests` runs bound DESFire tasks on a real card (the reserved test application, AES and DES). They are gated by the setting `secureKeys` in `hil.settings.json`, which is off in the sample, because they change a key on the card and put test credentials into the user's Credential Manager. `SECURE-KEYS.md` next to them lists the cases, the checklist for what needs a person (the PICC master key, a card pulled during a key change, MIFARE Classic and MAD, saving during a run, automatic mode, Format card, the migration) and how to clean up after an interrupted run.

- A setting has to be added in two places: `HilSettings` (the tests) and `Run-HilTests.ps1`, which reads the file with a parser of its own and refuses a name it does not know. `HilSettingsTests` fails when they drift apart.
- The cases have a fixture and a collection of their own (`HilSecureKeyFixture`, `HILSecureKeys`), because xunit creates the fixture of a collection also when every test in it is skipped. `HilFixture` would open the reader and delete the test application from the card then, even with `secureKeys` off. The gate does nothing at all unless the setting asks for it (`HilSecureKeyFixtureTests`); the collections of the project run one after the other.
- The HIL project sees the internals of the host (`InternalsVisibleTo`), so that the cases store their test keys with `WindowsCredentialKeyProvider.Store`, the code the application uses. `HilVault` keeps what it stored under `hil/<run>/...` and removes exactly that when it is disposed.
- The keys typed into a bound slot are decoys on purpose: they are the ones the card would accept where the vault key is refused, or the other way round, so a task that used the typed key could not pass.
- `HilSecureKeyScenarioSelfCheckTests` runs the same task builders and the same vault helper against a scripted reader and a dictionary, so a mistake in the set-up of a case shows up without a card.

## Trying an extension in RFiDGear while you develop it
RFiDGear reads its extensions from `%ProgramData%\RFiDGear\Extensions` once, at start-up. After a build, the extension and the support libraries it needs (`RFiDGear.ExtensionLibraries.*`) can be copied there for you, so you only restart RFiDGear.

- **Off unless asked for**, because a build is not always your own: test runs, clean checkouts and tools that build modified code would otherwise put their output into a real RFiDGear. Turn it on with the value `true` in one of these (the command line beats the local file, which beats the environment):
  - `dotnet build RFiDGear.Extensions/CardCheckAssistant -c Debug -p:DeployExtensionsToRFiDGear=true`
  - `RFiDGear.Extensions/deploy.local.props` (not in the repository, and only seen by the checkout that holds it; a second clone or worktree needs its own), containing `<Project><PropertyGroup><DeployExtensionsToRFiDGear>true</DeployExtensionsToRFiDGear></PropertyGroup></Project>`
  - the environment variable `RFIDGEAR_DEPLOY_EXTENSIONS=true`. With a local props file present it cannot switch the step off again; use `-p:DeployExtensionsToRFiDGear=false` for that.
- Only the extension, its libraries and their symbols are copied; never the contract, the SDK or the host. The last build replaces what is there, even an older build from another checkout; files are skipped only when they are identical. Nothing is deleted.
- The extension is copied first. If it cannot be replaced (RFiDGear is running and holds it), that is a warning and nothing else is copied, so the folder keeps one older set that belongs together; the last message says the deploy is not complete. Close RFiDGear and build again. It is an error only if your build treats warnings as errors.
- The copy has the platform of the build: an x64 build does not load into an x86 RFiDGear and the other way round; an AnyCPU build loads into both. `-p:RFiDGearExtensionsFolder=<folder>` copies somewhere else.
- The database driver that the order store will need is not copied; nothing opens the order database yet.

## The external control bridge: facts that bite
`Services/ExternalControl` (the host side) and `RFiDGear.Bridge.Contracts` (what a client references) are described in `CLAUDE.md`; the protocol is `RFiDGear.Bridge.Contracts/README.md` and the guide for client authors `CLIENT-GUIDE.md`. What to know before you change either:

- **The contract is a promise.** `RFiDGear.Tests/ApiSurface/RFiDGear.Bridge.Contracts.api.approved` freezes the public surface (regenerate with `RFIDGEAR_UPDATE_API_SNAPSHOT=1` and `--filter "FullyQualifiedName~BridgeContractsApiSurface"`; a mutation run that changes the contracts must include `FullyQualifiedName~ApiSurface` in its filter), `BridgeSamples` + `BridgeGolden` hold one value of every message and its JSON. Every DTO property has an explicit `[JsonPropertyName]`; the host reads requests strictly (an unknown member is refused) and a client reads answers tolerantly, so a new request member needs a new capability that the client has seen.
- **`ExecuteAllAsync` has to START on the WPF dispatcher.** Admission is its synchronous prefix: a refusal is an already faulted task (`InvalidOperationException` is busy, `ArgumentException` a bad report variable), a pending task is an admitted run. The run id is chosen by the bridge through the internal `IPreassignedRunExecution`. The host raises its events synchronously on the thread that changed the state: a handler only numbers, queues and returns, and a thread-static marker (`MarkAdmitting`, `s_starting`) tells the bridge's own raise from somebody else's at the same moment.
- **Admission and the claim of a mode are compare-and-swap, not locks around calls.** The window's callback must move a request from pending to admitting before it asks the host; the 5 s wait must move it to abandoned before it answers `uiUnresponsive`; whichever wins is the truth, so "nothing was started" is never said about a run that starts late. A client's claim on automatic mode carries the controller's start number and is only valid while that number is the one that is running.
- **Order matters in three places, and each has a test.** The journal line `started` is written and flushed before the host is asked; `ended` before the result is final; the result of the run that stops automatic mode comes before the notice that it stopped. A session is disposed (the pipe closed) before the next pipe instance is created, because one instance is allowed and a stuck write would otherwise turn the bridge off for good.
- **Events are one FIFO of at most 64 durable notices per client.** State notices (running, reader, project) are merged, results and mode changes are not; a client that lets 64 wait is disconnected (the results stay in the log), and so is one that does not take a notice within 10 s. A test of the cap has to wait less than that watchdog, or it passes for the wrong reason.
- **StreamJsonRpc**: the library has no maximum message size (`CappedReadStream` ends the connection before it allocates); an unknown method and a parameter that does not fit both arrive as `RemoteMethodNotFoundException` (codes -32601 and -32602); the default `error.data` carries a stack trace, so `BridgeJsonRpc` and `BridgeFault` always answer with our own data and the host's trace source stays off; a client has to override `GetErrorDetailsDataType` or it loses our data. A call from the host to the client (`resolveKey`) passes the cancellation token on the wire.
- **Nothing a client sent is logged.** The bridge logs the type of an exception, never its text, and ids and numbers, never a variable, a path, a UID, a key or a reference. A key lives in a `SecureKeyLease` (pinned, zeroed on dispose); the base64 text in the JSON message cannot be erased, which the documentation says openly.
- **Tests that build a main window through the bridge** pass a temporary journal folder (`externalControlJournalDirectory`) and a unique pipe name; tests wait with a bound (`WaitAsync`, a deadline), never with a bare `await` on something a defect could stop completing, because a hang stops a mutation run for ever.
