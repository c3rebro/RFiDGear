Extension packages (.rfext)

An extension has its own release cycle, and %ProgramData%\RFiDGear\Extensions is not writable for a normal user (and the DLLs of a running RFiDGear are locked there). An update is therefore a package that the person installs from the menu File > Install extension update... for their own user: with no administrator and no visit to a folder. The page Updates and extensions describes this from the point of view of the user.

Making a package (the side of the provider)

dotnet build RFiDGear.Extensions/CardCheckAssistant -c Release -p:Platform=x64 -p:PackExtension=true

writes bin\package\<id>-<version>-<platform>.rfext (PackExtension.targets; off unless asked). The package is for one platform, because the payload of an extension (the native sni.dll) is; a build for AnyCPU with native payload files is refused with a message. It holds the assembly of the extension, RFiDGear.ExtensionLibraries.*.dll and the ExtensionPayloadFile items of the project, no symbols. The project sets Version, ExtensionDisplayName and optionally ExtensionMinHostVersion; the file version of the assembly has to be the same number as Version, or the package is refused at install. Nothing in a package is executed.

The format

A zip file with extension.json at the top:

FieldContent
schema1
idthe assembly name, RFiDGear.Extensions.<...>
displayName, versionname and version
platformoptional x64 or x86 (written by the build); AnyCPU or none means nothing native in it. RFiDGear refuses a package of the other platform.
minHostVersion, notesoptional: the oldest RFiDGear that the package needs, and notes of the provider
filesfor each file the name and the sha256 of its content

The limits: only .dll and .pdb files with plain names; none of the assemblies the host owns and no other RFiDGear.Extensions* assembly; the archive holds exactly the listed files and no more; at most 64 files, 64 MB each and 256 MB in all. The sizes that an archive declares are not believed: it is read to the limit. Before it opens the archive, RFiDGear checks the end of the zip directory and refuses archives with too many entries, a directory that is too large, Zip64 markers or several disks. Nothing is extracted by the names in the archive.

Installing

  1. RFiDGear reads and checks the package, checks that this RFiDGear is at least minHostVersion and that the version is higher than the one that is used now (the machine-wide one or the user's).
  2. It unpacks into %LocalAppData%\RFiDGear\InstalledExtensions\.staging\<guid>, checks the file version of the assembly and reads the Authenticode signer.
  3. It asks the person (name, new and installed version, signer or "not signed", the notes of the provider, and that an extension is a program that runs with their rights).
  4. Then it moves the folder to InstalledExtensions\<id>\<version> in one rename. A version folder is never overwritten and never changed afterwards; the new version is used from the next start.

Trust

  • The SHA-256 in the manifest protects against a damaged or mixed-up package; it does not say who made it (the manifest is in the same archive).
  • The dialog shows who signed the assembly and whether the signature holds. Windows checks that (WinVerifyTrust with the generic action, no window, and no network for a revocation list). It is information for the person and no gate: an unsigned package, or one whose signature does not hold, can be installed after the question. The hash in the manifest is not tied to the signature: it says who signed the assembly, not that the whole package is the one that was signed.

Loading

  • At start-up the machine-wide folder is scanned as before, and the highest valid version folder of each extension under InstalledExtensions. An extension that is in both is loaded once: the higher file version wins, the machine-wide copy when they are equal; if the chosen one cannot be loaded, the other is tried.
  • A version folder whose extension failed the probe gets a marker .failed and is not chosen from the next start on: the next older installed version or the machine-wide copy is used. A marker .loaded names the newest version that was loaded.
  • RFiDGear tidies up: staging folders older than a day, the versions that failed and all but the two newest working versions (plus the newest one that is known to have loaded). Only the process that holds the lock file .lock in InstalledExtensions tidies.
Open is where packages are published. A release of RFiDGear carries exactly the three files of Pack-Release.ps1, and a release for an extension only must not become the "latest" release of the repository (it would break releases/latest/download/update.xml). A package as a fourth file or in a release of its own is a decision for the maintainer. An installed extension cannot be removed from the menu: delete its folder under InstalledExtensions.
