Requesting runs safely

The one rule. RFiDGear writes cards. A request that may have reached it has to be treated as if it had, until you have asked. So when startRun gets no answer (a timeout, a lost connection, an error without neverStarted: true), do not make a new request id and do not start the job again. Ask about the same request id with getRunResult. Only an error that carries neverStarted: true says that nothing was started, and only then may you try again.

Running a job

  1. Make the request id and write it down before you call. Build it from your job (an order number plus an attempt number, say). It is the only way to ask about the run if you lose the connection. While RFiDGear still knows the id (the last 1024, and after a restart only with the capability execution.journal), the same id with the same content never starts a second run. Past that it can: this is why a client asks after a doubt and does not send again.
  2. Pin the project. Load it with loadProject; note path, taskCount and revision as the state you approve for this job.
  3. Call startRun with the request id, the variables and the expectProjectPath, expectTaskCount and expectProjectRevision of the load. The answer comes when the run is admitted (running), not when it ends. On an error:
    • neverStarted: true (busy, noProjectLoaded, noReader, projectMismatch, uiUnresponsive, shuttingDown, notReady and others): nothing was started. Fix the cause or wait, and try again.
    • no neverStarted, a timeout or a lost connection: ask, do not send. (invalidRequest is a mistake of the program; the details name the field.)
  4. Wait for the end with getRunResult by request id and waitMs up to 30000; it returns as soon as the run ends or the wait runs out, and you ask again while it says running. Or listen to runCompleted and use getRunResult only as the fallback. Do not poll getStatus in a tight loop.
  5. Read the result (see The result of a run). bridgeFault as the reason means that RFiDGear could not give you a complete result and the card may have been touched.

The revision of the project (project.revision)

loadProject and the project of getStatus carry a revision: an opaque text that says in which state the project is in RFiDGear now. It covers what a save would write, so a change that was made in the window and not saved is part of it. It does not change when a run only leaves its results on the tasks: the data that a task read from a card is no part of it. The data that a write task is going to write is part of it. startRun with expectProjectRevision is refused (projectMismatch, neverStarted) before anything is touched when the project is in another state. The result carries projectRevision: the state the run started with.

  • Take the revision from loadProject, or from getStatus after you decided to approve that state, and pass it to startRun. Compare nothing else about it: do not parse it.
  • A revision is valid for one RFiDGear process. After a restart the same project has another one; the instanceId tells the processes apart. Do not store one for later.
  • A run changes the project it runs (the tasks write some of their own settings). The state that a run started with startRun leaves behind is recognized as the project it started with; not recognized are a change made in the window afterwards, what a run left that was started in the window, by automatic mode or by an extension, and a run whose state could not be read at its end. Such a state is refused: read the revision again and approve it.
  • If RFiDGear offers the capability but the answer to loadProject has no revision, do not start.

After a doubt, a lost connection or a restart

Connect again, make the hello and call getRunResult with the request id. The states are on the page The result of a run. For interruptedByRestart and unknown, look at the card (read it with a task that does not write) before you decide.

Catching up on results

getStatus tells you the number of the latest result (lastResultSeq). listRunResults with the number of the last result you have returns the results after it, oldest first, those of automatic mode too, up to the last 64. gap: true says that some were dropped from the history in between. A number that RFiDGear has not given out (you kept it over a restart) is refused with invalidRequest: check the instanceId first.

What not to do

  • Send a job again under a new request id after a doubt.
  • Poll getStatus in a tight loop to find out when a run ended.
  • Assume that a card is on the reader because the last status said so: read scanReader or let the result of the run tell you.
  • Treat unknown, or the end of the connection, as "nothing happened".
  • Run RFiDGear and the client with different rights, or start more than one RFiDGear.
  • Log variables, paths, UIDs or keys. Log the request id, the run id, the result number, the status and the kinds of errors.
