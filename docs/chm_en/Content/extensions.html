Writing an extension

An extension references only two assemblies, never RFiDGear.exe:

AssemblyContent
RFiDGear.Contractsthe services of the host (IRFiDGearExtensionHost and the services for project, execution, reader and culture). No MEF dependency.
RFiDGear.ExtensionSdkthe MEF-facing interface: [UiExtension], HostPlacement, IUIExtension, IUIExtensionDetails, IApplicationUIExtension, [SecureKeyProvider] and ISecureKeyProviderMetadata

Both keep the assembly version 1.0.0.0 (it changes only for a break, never with the version of the application), and their public surface is held by approved snapshots in the tests. A change fails the test and is accepted by regenerating the snapshot (RFIDGEAR_UPDATE_API_SNAPSHOT=1). The old locations of the SDK types in RFiDGear.exe forward, so that extensions that were built already keep working.

An extension with a window of its own

An extension with HostPlacement.Application implements IApplicationUIExtension. RFiDGear creates the exported class on the first click on its entry in the menu Extensions, never at start-up, and calls CreateContent(IRFiDGearExtensionHost host) on the user-interface thread each time the user opens it; the result is a new control for the window. The host disposes that content (and a different IDisposable data context) once when the window closes. The Card Check Assistant (RFiDGear.Extensions.CardCheckAssistant) is the first extension and the reference.

The rules

  • Discovery at start-up only, from %ProgramData%\RFiDGear\Extensions\RFiDGear.Extensions*.dll and from the folder of the user's installed packages. There is no hot loading: a new or removed extension needs a restart.
  • RFiDGear.Contracts.dll, RFiDGear.ExtensionSdk.dll and the MEF runtime are owned by the host. An extension must not carry private copies of them.
  • Do not [Import] IRFiDGearExtensionHost. The service does not exist yet when MEF composes the extensions, so it is not exported, and MEF leaves out an extension with an import it cannot satisfy without any error. Take the service from the argument of CreateContent.
  • The exported class is created on the first click and is shared afterwards: keep it stateless and put per-window state in the content. A constructor or CreateContent that throws is logged and shown to the user, and the next click tries again.
  • An extension that only needs a page can name it with Uri and implement just IUIExtension: it opens in a frame and its class is never created. Do not set Uri on an extension that implements IApplicationUIExtension: the page wins and CreateContent is not called.
  • A broken extension stops neither the others nor the application: MefHelper probes each DLL (parts, metadata, imports) before it goes into the container, logs a failure and skips that file.

A support library

Code that an extension needs besides the contract (services, a database driver, a PDF engine) goes in a library named RFiDGear.ExtensionLibraries.<Name>. The name must never start with RFiDGear.Extensions, in any letter case: the host hands every RFiDGear.Extensions*.dll to MEF, so a library called RFiDGear.ExtensionsNative.* would be loaded as an extension at every start-up. The library is net10.0 (no WPF), references no other RFiDGear project, compiles against the packages of the host (Serilog, GemBox.Pdf) without shipping a copy of them, and sits flat next to the extension that needs it. Keep library types out of the members and the constructor of the exported class: the checks of MEF cannot see a missing library, and the failure then shows up when the class is created or used.

What the library needs beside it besides that is the payload of the extension: for the Card Check Assistant the SQL driver (System.Data.SqlClient.dll and the sni.dll of the platform). The library names the files, the build of the extension copies them into its output folder, and from there the deploy step and the installers take them along.

Trying an extension while you develop it

RFiDGear reads its extensions once at start. After a build, the build can copy the extension and its libraries to %ProgramData%\RFiDGear\Extensions, so that you only restart RFiDGear. That is off unless you ask for it, because a build is not always your own (test runs, clean checkouts and tools that build modified code would otherwise put their output into a real RFiDGear):

  • dotnet build RFiDGear.Extensions/CardCheckAssistant -c Debug -p:DeployExtensionsToRFiDGear=true, or
  • the file RFiDGear.Extensions/deploy.local.props (not in the repository; a second clone needs its own) with <DeployExtensionsToRFiDGear>true</DeployExtensionsToRFiDGear>, or
  • the environment variable RFIDGEAR_DEPLOY_EXTENSIONS=true.

Only the extension, its libraries, their symbols and its payload are copied, never the contract, the SDK or the host. If the extension cannot be replaced (RFiDGear is running and holds it), that is a warning and nothing else is copied: close RFiDGear and build again. The copy has the platform of the build: an x64 build does not load into an x86 RFiDGear.
