One card, one approval, one run

A card should be written only after the program that owns the job has looked at it (its UID, the order, a duplicate check) and approved it. The project has a place for that: the task Check UID can name a variable instead of a UID, written as a dollar sign and a name, for example $EXPECTEDUID. The caller supplies the UID that it has approved as that variable (with startRun as one of the variables: { "name": "$EXPECTEDUID", "value": "04A1B2C3D4E5F6" }). The project does not change from card to card, so its revision does not either.

What the project has to look like

  • The first task is Check UID with the variable $EXPECTEDUID.
  • Every task that touches the card depends on it: its execute condition is the check with the result NoError; a task behind that one depends on the one before it. RFiDGear cannot tell which tasks write: a task without that condition runs whatever the check said.
  • A UID typed into the task is another thing: a question ("is this card that card?"), answered IsNotTrue, which a project may branch on. Only a variable is an approval.
  • The variable holds the UID in capital letters, as RFiDGear writes it in the result.

The task compares the variable with the UID of the card that the run itself read at its start (the cardUid of the result): a card that was swapped between the scan and the start is not the approved one. Another card, or a variable that is missing, empty or foreign, ends the check with CardNotExpected; the tasks that depend on it are skipped, and the run ends as failure, never as success and never as completedWithIntentionalFailures.

The flow for one card

Once per project (and again after RFiDGear was restarted, because a revision is valid for one process): hello (this flow needs project.load, reader.scan and execution.run and should have project.revision) and loadProject, with path, taskCount and revision as the approved state.

  1. scanReader. Go on only when the reader is ready and shows exactly one card. No reader, busy, no card or more than one card is a stop, and nothing has been started.
  2. Decide, in your own program: the job, the profile, the serial number, the list of cards that were written already. That is the approval. The UID of the scan is what you approve; it identifies the card for the job, it does not prove that the card is genuine.
  3. startRun with the request id of this job and this card (written down before the call, never reused for another card), the variable $EXPECTEDUID (or the name your project uses) set to the approved UID, and expectProjectPath, expectTaskCount and expectProjectRevision of the load. Never send it again: ask by the request id.
  4. Wait for the result. Record the card as written only when all of this holds: the status is success (or completedWithIntentionalFailures, if that is what your project means by done) and cardUid is the approved UID. Put the projectRevision of the result into the record of the job: it is the state the run started with. After an earlier run of yours it can be another than the one you approved, because the tasks write some of their own settings; RFiDGear refused the run before it started if the project was in a state that is neither the approved one nor one that a run of yours left behind.
  5. After a doubt ask getRunResult by the request id and never start the job again before you have looked at the card.
  6. Read back: load a separate project that only reads (a new loadProject and a new revision) and run it the same way. Do not read back with the project that writes.

Automatic mode with approval (autoMode.approval)

A station that handles one card after the other uses this mode: RFiDGear shows every card that is put on the reader to the client that started the mode, and runs the project for it only when that client approves it, once, for that card. The plain automatic mode runs every card and is not for writing.

startAutoMode with requireApproval: true. It needs stopOnDisconnect (the default), because nobody would be left to answer otherwise. approvalTimeoutMs (2000 to 120000, default 15000) is how long a card is waited for. Check the capability autoMode.approval first and ask hello for the events cardPresented, cardPresentationEnded and autoModeChanged. A start with approval is never agreed on when the mode is on already (autoModeActive). Leave a refused start alone: the mode that is on is not yours. Stop only a mode that your own client started, after getStatus shows it as the mode of a client (enabled and startedBy bridge), or let the operator replace it.

For every card:

  1. cardPresented says the presenceId, the uid, the projectRevision (the state of the project, read when the card was shown) and expiresAt. The same card taken away and put back is another presence with another id. Whether this UID was written already is yours to know: RFiDGear does not remember what you approved.
  2. Decide. The events go on while you decide, and the wait can end under you: drop the decision then and send nothing.
  3. approveCard with the presenceId, the variables of this one run ($EXPECTEDUID set to the approved UID) and expectProjectRevision (the one that came with the card: the run then starts only in exactly that state), or declineCard. Answer once, on the connection that started the mode. A variable that cannot be used is invalidRequest and the card still waits (for example a report target that is not a full path to a file in a folder that exists).
  4. cardPresentationEnded says how the wait ended.
ReasonConsequence
approved (with the runId)the run was admitted
declined, expired, stopped, clientLostnothing ran; the card stays remembered and is shown again only after it was taken away
projectChanged, notAdmitted, cardChangednothing ran; a card that is on the reader and was not processed is shown again as a new presence

What the mode holds to, and what stays with you

  • Without your approval nothing runs. An approval is for one card and one run and is used up by the first run, whatever it ends with.
  • The run reads the card itself, and that read is held to the approved UID before anything else is sent to the card: another card, or none, ends the run before its first task and stops the mode.
  • A late, repeated or foreign answer is approvalNotPending (1018): treat it as "this presence is over" and go on. Only the connection that started the mode can answer.
  • A lost connection ends the mode and runs nothing more. Never start a writing job again by yourself after you reconnected: start the mode again on purpose. RFiDGear remembers a card that it has shown or run and shows it again only after the reader was seen empty: take the card away and put it back, and it is shown as a new presence that needs a new approval (restarting the RFiDGear process forgets the card too).
  • loadProject and startRun are refused while the mode is on.
  • A run that fails does not stop the mode; a fault, a timeout or a lost reader does (autoModeChanged says why). After one of them look at the card before you start again.
  • The mode checks the approved UID itself, as said above. What it cannot know is which tasks write: only your project says that. So keep the Check UID with $EXPECTEDUID as the first task and let every writing task depend on it, as in the flow for one card; for a single startRun it is the only protection.
  • Never swap a project that writes for one that only reads while the mode is on: stop the mode, wait for autoModeChanged with enabled: false, load the other project, note its revision, take the card away and start the mode again.

The sample client has both flows (see The sample client).
