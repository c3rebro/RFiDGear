Methods and events

Every method takes one request and answers with one response. The capability is in brackets.

Methods

MethodEffectMain fields
hello (session)negotiates the protocol and delivers the capabilities, the chosen events, the instanceId and the limits Request: clientName, clientVersion, protocolMajorMin, protocolMajorMax, events. Response: product, appVersion, instanceId, protocol, sessionId, capabilities, limits
getStatus (status)says what is possible right now; it answers within two seconds even when the main window does not (stale is then set) startupComplete, readerInitializing, uiResponsive, stale, project (loaded, path, taskCount, revision), isRunning, activeRun, reader, lastResultSeq, autoMode
loadProject (project.load)replaces the loaded project with a file; unsaved changes in the window are lost. The path has to be a full path Request: path. Response: path, taskCount, revision
startRun (execution.run)runs the task list once and answers as soon as the run is admitted, not when it ends Request: requestId (1 to 64 characters of A-Z a-z 0-9 . _ : -), variables (up to 64 pairs of name/value), expectProjectPath, expectTaskCount, expectProjectRevision. Response: requestId, runId, state, duplicate
cancelRun (execution.cancel)asks a run to stop between two tasksRequest: requestId. Response: state, cancelRequested
getRunResult (execution.resultLookup)the state and the result of a run by request id or run id, optionally waiting for the end Request: requestId or runId, waitMs (up to 30000). Response: state, result
listRunResults (execution.resultLog)the results of all runs, those of automatic mode too, from a number onward, with an explicit gap Request: afterResultSeq, limit. Response: instanceId, results, gap, lastResultSeq
scanReader (reader.scan)reads the reader nowResponse: reader (name, state, hasCard, credentials with uid, typeCode, displayName, isPrimary)
startAutoMode, stopAutoMode (autoMode)continuous processing of cards stopOnDisconnect (on by default), requireApproval, approvalTimeoutMs (2000 to 120000, default 15000)
approveCard, declineCard (autoMode.approval)the answer about the card that was shown, once, for that presenceId, from the connection that started the mode presenceId; approveCard also variables and expectProjectRevision
registerKeyProvider (keys.provider)makes the client the supplier of card keys for the rest of the connection Request: ownRunsOnly. Response: providerId, timeoutMs, interactiveTimeoutMs, ownRunsOnly

The call from RFiDGear to the client

resolveKey (keys.provider), on IBridgeClientKeys: RFiDGear asks a client that registered for a card key. The rules are on the page Keys through external control.

Events

Events are notifications. A client names in hello the ones it wants, and only those are sent; each carries seq, sessionId and at.

EventCapabilityMeaning
runStarted, runCompletedevents.executiona run that this interface started; runCompleted is sent once per run
runningChangedevents.runninga run from anywhere started or ended
readerChangedevents.readerthe reader changed
projectChangedevents.projectthe project changed
autoModeChanged, autoRunCompletedevents.autoModethe mode was switched on or off; a card was processed. The result of the run that stops the mode comes before the notice that it stopped
cardPresented, cardPresentationEndedautoMode.approvala card was shown and waits for the answer (presenceId, uid, projectRevision, expiresAt); the wait ended, with a reason. Both go only to the connection that started the mode
shuttingDownevents.lifecycleRFiDGear is closing. Best effort: a connection that ends without this notice proves nothing
Events are hints. Nothing is replayed after a reconnect; the truth is getStatus, getRunResult and listRunResults. Keep the event handler short and never call RFiDGear from it: the notifications are delivered one after the other, and a handler that waits holds up the rest. Do not depend on the order of events of different kinds either.
