The result of a run

A result (RunResultDto) says how a run ended. A client trusts it only when taskOutcomes has exactly totalTasks entries: an incomplete result is never passed off as a complete one, but comes with the reason bridgeFault.

The fields

FieldContent
requestId, runIdthe request id (when a client started the run) and the run id
sourcebridge or autoMode
statussuccess, completedWithIntentionalFailures, failure, cancelled or timedOut
failureReasonnone, cancelled, timedOut, faulted, bridgeFault or unknown
totalTasks, failedTasksthe counts
startedAt, completedAtthe times
cardUidthe UID of the card that the run itself read at its start, when it is known
resultSeqthe number in the one sequence of results (runs of clients and of automatic mode); RFiDGear keeps the last 64
projectRevisionthe revision of the project that the run started with
presenceIdfor a card that was approved in automatic mode
taskOutcomesone entry per task (below)

When a run has succeeded

statusWhen
successevery task that ran ended without an error, and all tasks were reached
completedWithIntentionalFailuresa check said "no", or a task failed and a later one caught that with an execute condition. CardNotExpected can never end like this
failurea task failed and no later one reacted to it; CardNotExpected occurred; or the run ended before all tasks were reached
cancelled, timedOutthe run was stopped or took too long
A positive end of the task list is not the same as a card that holds what was meant. Check the card itself, and treat a run as confirmed only when cardUid is also the UID that you approved (see One card, one approval, one run).

A task in the result

FieldContent
positionthe place in the result, from 0: first the tasks the run reached, in the order it reached them, then the ones it did not reach
projectTaskIndexthe task number as the project writes it (free text: do not parse it)
taskTypeNamethe kind of task
isSuccesstrue when it ran and succeeded; false when it ran and failed; missing when it did not run or its result is not known
normalizedErrorCodethe normalized error code (NoError, AuthFailure, PermissionDenied, ProtocolConstraint, TransportError, Unknown, KeyUnavailable, CardNotExpected, ...); it never holds key material
skipReasonwhy the task did not run, when it did not
verificationDetailswhat a task that compares values compared (below)

The states of a lookup

getRunResult answers with a state:

stateMeaning
runningthe run is going on; ask again
completedit ended; the result is there unless the history dropped it (then you know it ended, but not how)
interruptedByRestartRFiDGear was closed or died while the run was going on. The card may have been written
unknownRFiDGear does not know the id: the request never arrived, or it is older than the last 1024. That is no proof that nothing was started.

Why a check failed: verificationDetails

A task that compares values can say what it compared, so that the record of a failed check holds more than "failed". Today only the DESFire task "Check: File Settings" has such details (kind desfire.fileSettings). They hold schemaVersion (1), kind, overallMatch, compareMode (all or any), applicationId, fileNumber, errorCode (notRead) and checks: one entry per setting in a fixed order (fileType, fileSize, communicationMode, accessRead, accessWrite, accessReadWrite, accessChange) with compared and result (match, mismatch, notRead or notCompared); a compared setting has expected and, when it could be read, actual, both as numbers (the size also has rule: exact, atLeast, atMost). Only numbers and fixed words, never a key, a text or the content of a file.

Something that a client does not know (another kind, a later schemaVersion, a new result word) is no error: show it as it is, and never decide anything on a word you do not know.
