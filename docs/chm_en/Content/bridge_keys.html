Keys through external control

A project can name a key by a reference to a provider instead of containing it (see Keys). The built-in provider bridge-client belongs to the connected client that called registerKeyProvider; RFiDGear then calls resolveKey on the client, inside the limits of the key registry. Without a registered client, a task that names the provider ends with KeyUnavailable and does not touch the card; the key typed into the project is no fallback.

How to register

  1. Call registerKeyProvider after hello. The answer gives the provider id (bridge-client), the time you have to answer (timeoutMs, interactiveTimeoutMs) and whether ownRunsOnly is in force.
  2. A person binds a key slot in a task dialog to that provider and types a reference of your choosing, such as orders/4711.
  3. When a task needs the key, RFiDGear calls resolveKey on you, with the reference, what the key is for (algorithm, usage, application, key number), the run, the task and the UID of the card.
  4. The registration ends with the connection; register again after you reconnect.

The rules for resolveKey

  • Implement it asynchronously and honor the token. It is canceled when the time is up (10 seconds, 5 minutes when a person may be asked) or the run is given up; a key that arrives later is thrown away.
  • Check the reference against what you serve. Any program of the user can put any reference in a project, and every run asks you while you are registered, whoever started it. Answer notAuthorized for a reference you do not recognize, and notFound for one you recognize without a key.
  • The answer is resolved with the key as base64 (1 to 32 bytes) or one of notFound, notAuthorized, invalidKey, unsupported. Anything else, or an exception, is a failure of your side.
  • RFiDGear does not ask you for the password or the PACK of a MIFARE Ultralight EV1 or an NTAG: this protocol has no name for those two kinds of key yet, so a slot of that kind that is bound to bridge-client ends with KeyUnavailable, and no resolveKey call is made. The key of an Ultralight C is a tripleDes2K key.
  • Never log the request or the answer, and do not keep the key longer than the answer needs. RFiDGear does neither, and keeps its copy only for the card operation, in a buffer that it erases. Neither side can erase the JSON text of the message: this protects against logs, files and command lines, not against a memory dump of a process of the same user.

Where a run comes from (keys.context)

When RFiDGear offers keys.context, every request for a key says where its run comes from:

FieldContent
sourcebridge (a run of a client of this interface, any client: compare the requestId), autoMode, gui (a run that the user started in the main window or with a start-up argument) or other (an extension, a button in a task dialog, a run that RFiDGear cannot place). A missing value reads as other.
requestIdfor a run of a client, the id that the client chose in startRun. Write it down before you call startRun, because the first request for a key can overtake the answer to startRun.
projectRevisionfor a run of a client, the revision that the run started with; compare it with the one you approved for that request

These are information. Whether you are asked, and what you may answer, does not change if you ignore them; the decision stays with your vault. A vault that gives out a key only for a request that is source: bridge, whose requestId it sent, whose projectRevision it approved and whose cardUid is the card it approved, has a release that is bound to one job.

ownRunsOnly in registerKeyProvider (default off) goes one step further: RFiDGear then answers notAuthorized itself for every run that was not started over this connection, and does not call you for it. That includes a run that the user starts in the window, a button in a task dialog, and a run that an earlier connection left behind. The run of a card that you approved in automatic mode is your own as well. The answer to the registration says whether the restriction is in force; check it. Send the field only when keys.context is offered: an older RFiDGear rejects a member it does not know.

What this protects against, and what it does not. The fields and the restriction protect against mix-ups and mistakes: a run from the window while your job was meant, a run of automatic mode, a project that was changed after you approved it, a request for a card you did not approve. They do not protect against a hostile program of the same Windows user: it has the same rights as the user. Treat a release that is bound to a run as a second lock, not as the only one.
