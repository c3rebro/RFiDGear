Bauen und testen

Voraussetzungen

  • Alles zielt auf .NET 10: der Host, die Testprojekte, das Beispiel-Plugin, die Verträge und der Card Check Assistant als net10.0-windows, der Beispielclient und die Bibliothek CardCheck als net10.0. global.json hängt das SDK an 10.0.x (ein neueres Vorschau-SDK auf dem Rechner würde sonst gewählt).
  • Visual Studio 2022 kann net10.0 nicht: verwenden Sie Visual Studio 2026 oder die dotnet-Befehlszeile.
  • Das Projekt ist ein WPF-Programm für Windows (x64 und x86).

Befehle

dotnet build RFiDGear.sln -c Debug
dotnet build RFiDGear.sln -c Release

dotnet test RFiDGear.Tests/RFiDGear.Tests.csproj
dotnet test RFiDGear.Tests/RFiDGear.Tests.csproj --filter "FullyQualifiedName~MeineKlasse.MeineMethode"

Die Tests

  • RFiDGear.Tests sind die Einheits- und Integrationstests, ohne Leser. Sie laufen auf xunit.v3 (das Paket xunit.v3.mtp-off; das .NET-10-SDK verweigert sonst, ein auf Microsoft.Testing.Platform gebautes Projekt über den VSTest-Weg von dotnet test auszuführen). Die Testprojekte sind deshalb ausführbare Dateien; dotnet test und --filter funktionieren wie gewohnt.
  • Ein Test, der WPF berührt, braucht einen STA-Thread (StaTestRunner.cs). Ein Test, der ein Hauptfenster baut, übergibt einen temporären Journalordner und einen eindeutigen Pipe-Namen.
  • Freigegebene Schnappschüsse halten die öffentliche Fläche der Verträge fest (RFiDGear.Tests/ApiSurface/). Eine Änderung lässt den Test scheitern; Sie nehmen sie an, indem Sie den Schnappschuss neu erzeugen: RFIDGEAR_UPDATE_API_SNAPSHOT=1 und der Filter BridgeContractsApiSurface (oder ExtensionSdkApiSurface). Ein Mutationslauf, der die Verträge ändert, muss FullyQualifiedName~ApiSurface im Filter haben.
  • BridgeSamples und BridgeGolden halten je einen Wert jeder Nachricht der externen Steuerung und sein JSON: eine Änderung der Leitung ist ein Unterschied in einem Test.
  • Die Tests der Hilfe (HelpFilesTests, HelpFileTests) lesen die echten Dateien unter docs.

Hardwaretests

RFiDGear.HIL.Tests laufen an einem echten Leser mit echten Karten. Sie gehören nicht zum normalen Testlauf; die Lösung übersetzt sie nur. Der Start geht über Run-HilTests.bat; hil.settings.json daneben schaltet die Fälle ein: readerScan, interactive, secureKeys, cardWrites und readerKind (auto, elatec oder pcsc). Die Prüflisten stehen in EXTERNAL-CONTROL.md, CLASSIC.md, ULTRALIGHT.md, SECURE-KEYS.md, SAM-AV3.md und SAM-PICC.md. Fälle mit cardWrites schreiben auf Karten: verwenden Sie Karten, die Sie nicht mehr brauchen.

Erweiterungen, Hilfe, Installer

  • Erweiterungen beim Entwickeln ausprobieren und Pakete bauen: siehe Erweiterungen schreiben und Erweiterungspakete.
  • Die Hilfe baut docs/Build-Help.ps1 mit hhc.exe von HTML Help Workshop; die übersetzten .chm liegen neben ihren Quellen im Repository, weil ein normaler Bau (und jeder Test) HTML Help Workshop nicht braucht.
  • Die Installer (RFiDGearBundleSetup und die beiden MSI-Projekte) benutzen WiX 3.14 und werden getrennt gebaut, nicht mit dotnet build: zuerst Host und Beispiel-Plugin im Release für die Plattform, dann die MSI-Projekte, dann das Bündel, mit dem MSBuild von Visual Studio 2026. Ein Release macht RFiDGearBundleSetup\Build-Release.ps1, dann Sign-Release.ps1 und Pack-Release.ps1 (Make-Release.bat führt die drei aus). Die Version steht von Hand in RFiDGear.csproj, Bundle.wxs und update.xml; ein Test stoppt ein Release, in dem sie abweichen. Das Zertifikat liegt nicht im Repository (RFIDGEAR_SIGN_PFX, RFIDGEAR_SIGN_PASSWORD).
