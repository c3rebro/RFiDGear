Erweiterungspakete (.rfext)

Eine Erweiterung hat einen eigenen Veröffentlichungsrhythmus, und %ProgramData%\RFiDGear\Extensions ist für einen normalen Benutzer nicht beschreibbar (und die DLLs eines laufenden RFiDGear sind dort gesperrt). Ein Update ist deshalb ein Paket, das die Person im Menü Datei > Erweiterungs-Update installieren... für ihren eigenen Benutzer installiert: ohne Administrator und ohne einen Ordner anzufahren. Die Seite Updates und Erweiterungen beschreibt das aus der Sicht des Benutzers.

Ein Paket bauen (die Seite des Anbieters)

dotnet build RFiDGear.Extensions/CardCheckAssistant -c Release -p:Platform=x64 -p:PackExtension=true

schreibt bin\package\<id>-<version>-<platform>.rfext (PackExtension.targets; aus, solange es nicht verlangt wird). Das Paket gilt für eine Plattform, weil die Nutzlast einer Erweiterung (die native sni.dll) es ist; ein Bau für AnyCPU mit nativen Nutzlastdateien wird mit einer Meldung abgelehnt. Es enthält die Assembly der Erweiterung, RFiDGear.ExtensionLibraries.*.dll und die ExtensionPayloadFile-Einträge des Projekts, keine Symbole. Das Projekt setzt Version, ExtensionDisplayName und wahlweise ExtensionMinHostVersion; die Dateiversion der Assembly muss dieselbe Zahl wie Version sein, sonst wird das Paket bei der Installation abgelehnt. Nichts in einem Paket wird ausgeführt.

Das Format

Eine Zip-Datei mit extension.json an oberster Stelle:

FeldInhalt
schema1
idder Assemblyname, RFiDGear.Extensions.<...>
displayName, versionName und Version
platformwahlweise x64 oder x86 (vom Bau geschrieben); AnyCPU oder keines heißt: nichts Natives darin. RFiDGear weist ein Paket der anderen Plattform zurück.
minHostVersion, noteswahlweise: das älteste RFiDGear, das das Paket braucht, und Hinweise des Anbieters
filesje Datei name und das sha256 ihres Inhalts

Die Grenzen: nur .dll- und .pdb-Dateien mit schlichten Namen; keine Assembly, die dem Host gehört, und keine andere RFiDGear.Extensions*-Assembly; das Archiv enthält genau die aufgeführten Dateien und keine mehr; höchstens 64 Dateien, 64 MB je Datei und 256 MB insgesamt. Die Größen, die ein Archiv angibt, werden nicht geglaubt: es wird bis zur Grenze gelesen. Vor dem Öffnen prüft RFiDGear das Ende des Zip-Verzeichnisses und weist Archive mit zu vielen Einträgen, zu großem Verzeichnis, Zip64-Markern oder mehreren Datenträgern ab. Nichts wird unter den Namen im Archiv entpackt.

Das Installieren

  1. RFiDGear liest und prüft das Paket, prüft, dass dieses RFiDGear mindestens minHostVersion ist und dass die Version höher als die jetzt verwendete ist (die des gemeinsamen Ordners oder die des Benutzers).
  2. Es entpackt in %LocalAppData%\RFiDGear\InstalledExtensions\.staging\<guid>, prüft die Dateiversion der Assembly und liest den Authenticode-Unterzeichner.
  3. Es fragt die Person (Name, neue und installierte Version, Unterzeichner oder „nicht signiert“, die Hinweise des Anbieters und dass eine Erweiterung ein Programm ist, das mit ihren Rechten läuft).
  4. Dann verschiebt es den Ordner mit einer einzigen Umbenennung nach InstalledExtensions\<id>\<version>. Ein Versionsordner wird nie überschrieben und danach nie verändert; die neue Version wird ab dem nächsten Start verwendet.

Vertrauen

  • Der SHA-256 im Manifest schützt gegen ein beschädigtes oder vertauschtes Paket; er sagt nicht, wer es gemacht hat (das Manifest liegt im selben Archiv).
  • Der Dialog zeigt, wer die Assembly signiert hat und ob die Signatur hält. Das prüft Windows (WinVerifyTrust mit der allgemeinen Aktion, ohne Fenster und ohne Netz für eine Sperrliste). Es ist eine Information für die Person und kein Tor: ein unsigniertes Paket, oder eines, dessen Signatur nicht hält, lässt sich nach der Frage installieren. Der Hash im Manifest ist nicht an die Signatur gebunden: sie sagt, wer die Assembly signiert hat, nicht, dass das ganze Paket das ist, was signiert wurde.

Das Laden

  • Beim Start wird der gemeinsame Ordner wie bisher durchsucht, dazu der höchste gültige Versionsordner jeder Erweiterung unter InstalledExtensions. Eine Erweiterung, die in beiden ist, wird einmal geladen: die höhere Dateiversion gewinnt, bei Gleichheit die Kopie des gemeinsamen Ordners; lässt sich die gewählte nicht laden, wird die andere versucht.
  • Ein Versionsordner, dessen Erweiterung die Prüfung nicht bestand, bekommt eine Marke .failed und wird ab dem nächsten Start nicht mehr gewählt: die nächstältere installierte Version oder die Kopie des gemeinsamen Ordners wird verwendet. Eine Marke .loaded bezeichnet die neueste Version, die geladen war.
  • RFiDGear räumt auf: Staging-Ordner, die älter als einen Tag sind, die gescheiterten Versionen und alle außer den zwei neuesten funktionierenden Versionen (plus der neuesten, die bekanntlich geladen war). Nur der Prozess, der die Sperrdatei .lock in InstalledExtensions hält, räumt auf.
Offen ist, wo Pakete veröffentlicht werden. Ein Release von RFiDGear trägt genau die drei Dateien von Pack-Release.ps1, und ein Release nur für eine Erweiterung darf nicht das „neueste“ Release des Repositorys werden (es würde releases/latest/download/update.xml brechen). Ein Paket als vierte Datei oder in einem eigenen Release ist eine Entscheidung des Betreuers. Eine installierte Erweiterung lässt sich nicht über das Menü entfernen: löschen Sie ihren Ordner unter InstalledExtensions.
